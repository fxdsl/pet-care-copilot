# 第九周：社交互动、推荐信息流与前端基础重构

> 完成时间：2026-08-23  
> 本周数据库版本：Flyway `V7`  
> 本周目标：把第八周“能发布帖子”的社区升级为可交流、可推荐、可治理的社区，并把单体 Vue 页面迁移为正式的路由化前端。

## 1. 本周最终完成情况

第九周已经完成以下能力：

- **评论：支持一级评论和对一级评论的回复，作者可删除自己的评论。**
- **点赞与收藏：接口可重复调用，MySQL 唯一键保证不会重复计数。**
- 关注：可关注/取消关注其他活跃用户，禁止关注自己。
- 信息流：支持 `LATEST`、`HOT`、`FOLLOWING`、`NEARBY` 四种模式。
- 推荐：热门榜采用带时间衰减的 Redis ZSet，附近内容采用 Redis GEO；Redis 不可用时自动回源 MySQL。
- 举报治理：用户可举报帖子、评论或用户；`ADMIN` 和 `MODERATOR` 可处理举报并隐藏违规内容。
- 养宠打卡：MySQL 保存事实，Redis Bitmap 保存按月快速视图。
- 运营统计：Redis HyperLogLog 统计社区日 UV，MySQL 统计待处理举报数。
- Redis 教学覆盖：Set、Hash、ZSet、GEO、Bitmap、HyperLogLog、Lua 均有真实业务落点。
- 前端重构：删除 1034 行的单体 `App.vue` 旧实现，引入 Vue Router、Pinia 和按需 Element Plus。
- 页面拆分：普通用户布局与管理布局完全分开，页面使用懒加载路由。
- UI 升级：社区改为参考成熟社交产品信息架构的三栏时间线，补齐加载、空、错误、重试、评论抽屉、编辑弹窗和移动端布局。

本周没有把 Redis 当数据库。点赞、收藏、关注、评论、举报和打卡的最终事实都在 MySQL；Redis 丢失后仍能回源或重建。

## 2. 本周架构

```text
Vue 3 页面
  ├─ Vue Router：真实 URL、角色守卫、页面懒加载
  ├─ Pinia：登录用户与令牌状态
  └─ CommunityView：信息流、评论、互动、举报、打卡
             │ Bearer JWT
             ▼
Spring Boot Controller
  ├─ CommunityPostController
  ├─ CommunitySocialController
  └─ CommunityModerationController
             ▼
Service 事务层
  ├─ CommunityPostService
  ├─ CommunitySocialService
  └─ CommunityRecommendationService
       │                   │
       ▼                   ▼
MyBatis + MySQL         Redis 副本/索引
  最终事实                Set / Hash / ZSet / GEO
                         Bitmap / HLL / Lua
```

关键原则：

1. 浏览器传来的用户 ID 不可信，所有当前用户都从 JWT 的 `Principal` 取得。
2. MySQL 关系表的联合主键负责幂等，Redis 只负责快速读取、排序和近似统计。
3. Service 先完成数据库事务，再更新可失败的 Redis 副本。
4. 管理端路由由 Spring Security 限制为 `ADMIN/MODERATOR`；Vue 路由守卫只改善体验，不能替代后端授权。
5. 第八周旧页面被新路由页面替换后直接删除，不保留隐藏的双实现。

### 3.2 登录和角色守卫

```ts
router.beforeEach(async (to) => {
  const auth = useAuthStore()
  await auth.bootstrap()
  if (to.meta.public) return auth.user ? defaultPath(auth.user.role) : true
  if (!auth.user) return { name: 'login', query: { redirect: to.fullPath } }
  const roles = to.meta.roles ?? to.matched.find((item) => item.meta.roles)?.meta.roles
  if (roles && !roles.includes(auth.user.role)) return defaultPath(auth.user.role)
  return true
})
```

- `USER/VERIFIED_SELLER` 默认进入 `/app/community`。
- `ADMIN` 默认进入 `/manage/knowledge`。
- `MODERATOR` 默认进入 `/manage/moderation`。
- 普通用户布局不显示治理菜单；管理布局不显示智能问答和宠物档案。
- 后端仍会再次鉴权，即使手工修改前端 URL 也不能越权。

### 3.3 社区交互与失败回滚

点赞按钮先进行乐观更新，减少等待感；接口失败时恢复旧值：

```ts
async function toggleLike(post: CommunityPost): Promise<void> {
  const next = !post.viewerLiked
  post.viewerLiked = next
  post.likeCount += next ? 1 : -1
  try {
    const result = await setPostLike(post.id, next)
    post.viewerLiked = result.active
    post.likeCount = result.count
  } catch (cause) {
    post.viewerLiked = !next
    post.likeCount += next ? -1 : 1
    ElMessage.error(readable(cause))
  }
}
```

最终状态仍以接口返回的 `active/count` 为准，所以快速点击、重复请求或网络重试不会让页面永久显示错误计数。

### 3.5 问答页固定外壳与双滚动区补强

2026-08-23 根据实际使用反馈补充：原 `.chat-page` 使用 `min-height`，消息增多后会撑高整个文档，滚轮会把顶部导航、会话栏和输入区一起推走。现在只在问答路由给用户布局增加 `chat-route`，将外壳限制为 `100dvh`；社区、档案和账号页仍保持正常文档滚动。

```css
.user-shell.chat-route {
  display: grid;
  overflow: hidden;
  height: 100dvh;
  min-height: 0;
  grid-template-rows: auto minmax(0, 1fr);
}

.conversation-list,
.message-stream {
  overflow-y: auto;
  min-height: 0;
  overscroll-behavior: contain;
  scrollbar-gutter: stable;
}
```

会话侧栏被拆成固定标题和 `.conversation-list` 两部分；问答主区使用 `auto auto minmax(0,1fr) auto auto` 网格行，固定标题、筛选和输入框，只让 `.message-stream` 滚动。`overscroll-behavior: contain` 防止内部列表滚动到边缘后继续推动外层页面。新增消息或加载历史后调用 `scrollMessagesToEnd()`，只调整消息容器的 `scrollTop`。

真实浏览器验证结果：

| 指标 | 桌面端结果 | 说明 |
|---|---:|---|
| 视口/文档高度 | `720 / 720` | 外层页面无可滚动溢出 |
| `window.scrollY` | `0` | 滚动历史和消息后页面未移动 |
| 历史栏 | `clientHeight=460`、`scrollHeight=2038` | 具备独立滚动条 |
| 消息区 | `clientHeight=328`、`scrollHeight=2486` | 具备独立滚动条 |
| 实际滚动 | 历史 `700`、消息 `930` | 两个容器互不影响 |

在 `390 × 844` 手机视口中，文档高度等于 844、`window.scrollY=0`，消息区独立滚动；输入框底部约 755px，底部导航从约 788px 开始，没有互相遮挡。

#### 3.7.5 打开帖子详情后立即更新浏览量

信息流列表只负责展示，不把自动曝光当作浏览；用户点击帖子进入详情抽屉时，前端必须调用详情接口：

```http
GET /api/v1/community/posts/{postId}
Authorization: Bearer <accessToken>
```

- Path：`postId:string`，必填，目标帖子 ID。
- Query：无。
- Body：无。
- 成功响应：`200 CommunityPostResponse`，其中 `viewCount` 已包含本次 Redis 浏览增量。
- 主要错误：`401` 未登录、`404` 帖子不存在或不可公开访问、`503` 依赖服务不可用。

前端同时请求详情和评论，但使用 `Promise.allSettled` 隔离结果。评论加载失败不会让已经成功的详情计数失效；详情成功后同时更新抽屉和原信息流卡片：

```ts
const [detailResult, commentResult] = await Promise.allSettled([
  getCommunityPost(post.id),
  listCommunityComments(post.id),
])

if (detailResult.status === 'fulfilled') {
  selectedPost.value = detailResult.value
  post.viewCount = detailResult.value.viewCount
}
```

后端 `publicDetail()` 把 `viewDelta` 写入 Redis Hash，并在响应中返回“MySQL 基数 + Redis 待回写增量”；`CommunityCounterFlushService` 每 10 秒批量回写 MySQL。前端不等待 MySQL 回写，因此用户打开详情后能立即看到增加后的数字。

真实浏览器验收结果：

| 验收项 | 结果 |
|---|---|
| `1440 × 900` 三栏滚动 | 左 `scrollTop=310`、中 `720`、右 `240`，`window.scrollY=0` |
| 中栏一键回顶 | 中栏回到 `0`；左右仍分别保持 `310/240` |

### 4.3 MyBatis 幂等写入

```xml
<insert id="insertLike">
    INSERT IGNORE INTO community_post_like (post_id, user_id, created_at)
    VALUES (#{postId}, #{userId}, #{createdAt})
</insert>

<update id="synchronizeLikeCount">
    UPDATE community_post p
    SET p.like_count = (
        SELECT COUNT(*) FROM community_post_like l WHERE l.post_id = p.id
    )
    WHERE p.id = #{postId}
</update>
```

不能使用“页面当前计数 + 1”作为数据库事实。重复 `PUT like` 时 `INSERT IGNORE` 不新增关系，之后重新 `COUNT(*)` 得到正确计数。

## 5. Redis 的各种用法

| Key 示例 | 数据结构 | 内容示例 | TTL | 写入/读取 | 丢失或故障处理 |
|---|---|---|---|---|---|
| `community:user:u1:likes` | Set | 成员 `post-1` | 30 天，互动时续期 | 点赞后写；可用于用户状态加速 | MySQL `community_post_like` 可重建 |
| `community:user:u1:favorites` | Set | 成员 `post-2` | 30 天，互动时续期 | 收藏后写 | MySQL 收藏表可重建 |
| `community:user:u1:following` | Set | 成员 `user-2` | 30 天，关注时续期 | 关注后写 | MySQL 关注表可重建 |
| `community:post:social:p1` | Hash | `likeCount=8` | 6 小时 | Lua 与关系 Set 同步更新 | 帖子查询回源 MySQL |
| `community:feed:hot` | ZSet | `postId → hotScore` | 6 小时 | 发布/互动后刷新；热门流读取 | 空 Key 启动重建，异常回源 MySQL |
| `community:post:geo` | GEO | `postId → 经纬度` | 不设置；启动全量重建 | 发布位置写入；附近流半径检索 | 删除旧 Key 后从已发布帖子重建；异常按地区回源 |
| `community:report:queue` | ZSet | `reportId → createdEpoch` | 待处理期间保留 | 举报写入；处理后移除 | 管理列表最终查询 MySQL `PENDING` |
| `community:checkin:u1:2026-08` | Bitmap | offset 22=true | 430 天 | 打卡写入 | 连续天数和月次数仍从 MySQL 计算 |
| `community:feed:uv:20260823` | HyperLogLog | 用户 ID | 35 天 | 每次加载信息流 PFADD | 失败时仅统计变小，不影响业务 |

### 5.1 Lua 为什么只做缓存原子同步

```java
private static final DefaultRedisScript<Long> SYNC_RELATION = new DefaultRedisScript<>(
    "if ARGV[1] == '1' then redis.call('SADD', KEYS[1], ARGV[2]) "
  + "else redis.call('SREM', KEYS[1], ARGV[2]) end; "
  + "redis.call('HSET', KEYS[2], ARGV[3], ARGV[4]); return 1",
    Long.class
);
```

这段 Lua 在 Redis 内一次完成：

1. 把帖子 ID 加入/移出用户关系 Set。
2. 把 MySQL 重新计算出的计数写入帖子 Hash。

它没有取代 MySQL 事务。Java 调用顺序是：验证公开帖子 → MySQL 写关系 → MySQL 同步计数 → 查询最终状态/计数 → Lua 更新缓存。Redis 失败只记录警告，不回滚已经正确提交的 MySQL 事实。

### 5.2 热度计算

```java
double ageHours = Math.max(0,
    Duration.between(post.publishedAt(), Instant.now()).toMinutes() / 60.0);
double engagement = post.likeCount() * 3.0
    + post.commentCount() * 4.0
    + post.favoriteCount() * 5.0
    + Math.log1p(post.viewCount());
double score = engagement / Math.pow(ageHours + 2.0, 1.15);
```

收藏权重高于点赞，评论高于点赞，浏览量使用对数抑制大数。分母随发布时间增长，旧帖子会自然衰减，不会永久霸榜。Redis 为空时先从 MySQL 取最多 500 个候选重建；Redis 异常时直接在 Java 中计算并分页。

### 5.3 附近信息流

Redis GEO 使用 `longitude, latitude` 顺序保存位置。请求传入当前位置和 `radiusKm` 后按距离升序取帖子 ID，再使用 MyBatis 批量读取完整帖子并保持 GEO 顺序。若 Redis 不可用，则在 MySQL 中取相同地区/候选位置，使用球面距离公式筛选，保证功能可降级而不是直接 500。

### 5.4 列表避免 N+1

帖子列表不能对每张卡片分别查询“是否点赞、是否收藏、是否关注作者”。`decoratePosts` 一次收集所有帖子 ID 和作者 ID，然后执行三次批量 SQL：

```java
Set<String> likes = new HashSet<>(mapper.findLikedPostIds(userId, postIds));
Set<String> favorites = new HashSet<>(mapper.findFavoritePostIds(userId, postIds));
Set<String> follows = new HashSet<>(mapper.findFollowedUserIds(userId, authorIds));
```

最后在内存中填充 `viewerLiked/viewerFavorited/viewerFollowsAuthor`。这样列表 20 张卡片也不是 60 次关系 SQL。

- Query：`status` 可空或 `PENDING/RESOLVED/REJECTED`；`page` 默认 0；`size` 默认 20、限制 1～100。
- Path/Body：无。
- 成功 `200`：`{ items: CommunityReportResponse[], page, size, total }`；待处理优先、同状态按创建时间排序。
- 错误：400（status 无效）、401、403、503。

### 11.4 处理举报

`PUT /api/v1/moderation/community/reports/{reportId}`

- 权限：`ADMIN` 或 `MODERATOR`。
- Path：`reportId`，举报 UUID。
- Query：无。
- Body：

```json
{
  "action": "HIDE_CONTENT",
  "note": "内容包含危险用药建议",
  "version": 1
}
```

| 字段 | 必填 | 规则 |
|---|---:|---|
| `action` | 是 | `NO_ACTION/HIDE_CONTENT/WARN_USER` |
| `note` | 否 | 最长 1000 字符 |
| `version` | 是 | 最近响应中的正整数版本 |

- 成功 `200`：处理后的 `CommunityReportResponse`，状态为 `RESOLVED`，版本增加。
- `HIDE_CONTENT`：帖子改为 `HIDDEN` 并移出缓存/推荐；评论改为 `HIDDEN` 并重算评论数。
- 错误：400（动作无效/举报不存在）、401、403、409（已由其他管理人员处理）、503。

### 11.5 今日运营摘要

`GET /api/v1/moderation/community/analytics/today`

- 权限：`ADMIN` 或 `MODERATOR`。
- Path/Query/Body：无。
- 成功 `200`：`{ "date":"2026-08-23", "approximateFeedUv":18, "pendingReports":2 }`。
- `approximateFeedUv` 是 HLL 近似值，不可用于计费；`pendingReports` 是 MySQL 精确值。
- 错误：401、403、503。Redis 不可用时 UV 返回 0，但举报精确数仍可返回。

## 13. 关键业务调用顺序

### 13.1 点赞

```text
PUT /posts/{id}/like
 → JWT 取得 userId
 → 确认帖子为 PUBLISHED
 → INSERT IGNORE 点赞关系
 → 按关系表 COUNT 并同步 community_post.like_count
 → 查询最终 active/count
 → Lua 同步 Redis Set + Hash（失败可忽略）
 → 删除共享详情缓存
 → 刷新该帖热门分数
 → 返回最终状态
```

### 13.2 创建二级评论

```text
POST /posts/{id}/comments { parentId, content }
 → 检查公开帖子
 → parentId 存在时查询父评论
 → 校验父评论属于当前帖子且 depth=0
 → 写入 depth=1、rootId=parent.id
 → 重新统计公开评论数
 → 清理帖子详情缓存并刷新热度
```

项目只允许两级结构，避免无限嵌套导致移动端难以阅读。回复二级评论时接口返回 400，并提示回复一级评论。

### 13.3 举报并隐藏内容

```text
用户提交举报
 → 校验目标存在
 → MySQL 唯一键阻止重复举报
 → 写 PENDING 举报
 → Redis ZSet 加入审核优先队列

管理员处理
 → WHERE status=PENDING AND version=? 乐观锁更新
 → HIDE_CONTENT 时隐藏帖子/评论
 → 删除详情、热榜和 GEO，或重新汇总评论数
 → 从举报 ZSet 移除
 → 返回新的 version
```

两个管理员同时打开同一举报时，只允许第一个版本匹配的请求成功。第二个请求得到 409，前端提示刷新，不会覆盖已有处理结果。

## 16. 故障排查

### 16.1 附近流提示需要位置

- 第一次点击“附近”时浏览器会请求定位权限。
- 拒绝权限后不会伪造坐标，应改用最新/热门/关注流，或在发帖表单重新点击“使用当前位置”。
- 请求必须同时传 `latitude` 和 `longitude`，坐标顺序不能颠倒。

### 16.2 Redis 停止后社区是否不能使用

不是。预期降级如下：

- 最新、关注、评论、点赞、收藏、举报、打卡事实仍由 MySQL 完成。
- 热门流在 Java 中使用 MySQL 候选重新计算。
- 附近流使用 MySQL 候选和距离公式。
- 日 UV 返回 0 或缺少一部分访问，仅影响近似运营数据。
- Redis 恢复并重启 Java 后，启动预热会删除旧热门/GEO Key，再从 MySQL 重建，避免已隐藏或已删除帖子残留。

### 16.3 点赞数偶尔与旧页面不同

第九周接口每次写操作都会以关系表 `COUNT(*)` 为最终计数，并清理详情缓存。若浏览器仍展示旧值：

1. 在 Network 查看接口返回的 `active/count`。
2. 确认页面使用响应值，而不是只做本地加减。
3. 刷新帖子详情；共享缓存被清理后会从 MySQL 回源。

### 16.4 举报处理返回 409

说明当前页面持有的 `version` 已过期，其他管理员已经处理了该举报。刷新举报列表，不要自动覆盖对方结果。

### 16.5 刷新子页面出现服务器 404

Vite 开发服务器已支持 SPA 回退。部署到 Nginx 时需要把未知前端路径回退到 `index.html`，但 `/api/` 仍反向代理到 Spring Boot，不能把 API 错误也回退成 HTML。

示例：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}

location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
```

## 19. 第十周替换的非流式问答核心代码归档

第九周问答页使用一次性 HTTP 调用，只有请求全部完成后才把助手消息加入界面。代表性流程如下，现仅用于理解迁移，不再作为问答页主流程运行：

const response = await sendQuestion({
  question: question.value,
  conversationId: conversationId.value,
  petProfileId: selectedPetId.value || undefined,
})
conversationId.value = response.conversationId

  role: 'ASSISTANT',

这段实现无法显示检索阶段、模型生成过程和心跳；网络在响应结束前中断时也不知道服务端是否已经保存消息。第十周改为固定 `requestId` 的 POST SSE，使用 `Last-Event-ID` 重连，逐个处理 `stage/token/result/done/error/cancelled`，并提供停止生成。非流式 Controller 仍保留为调试入口，但和 SSE 共用 `ChatService`，没有保留第二套检索或持久化逻辑。
