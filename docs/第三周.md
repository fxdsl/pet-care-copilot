# 第三周：标准 MyBatis、知识向量化与基础 RAG

## 1. 本周完成结果

第三周已经把第二周的“知识可导入”推进为“知识可检索、回答可追溯”的基础 RAG 版本，并落实了 Java 工程规范要求：

1. Java 数据访问从 `JdbcTemplate` 全部迁移到标准 MyBatis，未使用 MyBatis-Plus。
2. Java 代码按 `controller/service/client/config/exception/data` 分层，实体、请求、响应和内部传输对象分别存放。
3. FastAPI 在知识导入时生成 256 维本地向量，MySQL 保存向量及模型元数据。
4. 问答时由 MyBatis 读取候选知识，FastAPI 计算余弦相似度并执行 Top-K 召回。
5. 采用混合问答：有可靠上下文时返回可追溯 RAG 答案；未命中时调用百炼通用知识并明确标记无来源。
6. 无 API Key 时使用本地抽取式答案；检测到 `DASHSCOPE_API_KEY` 后自动使用阿里云百炼生成式回答，调用失败仍会降级。
7. 前端升级为“第三周 · 基础 RAG 版”，可显示实际来源和相关度。
8. 新增和重构的 Java、Python、TypeScript、SQL 与 XML 代码均补充了中文职责或关键逻辑注释。

本周的核心原则是：先建立一个可运行、可测试、可解释的 RAG 基线，再在第四、第五周逐步增强模型能力和检索质量。

## 2. 完整调用链

### 2.1 知识导入

```text
导入请求
  → Spring Boot KnowledgeController
  → KnowledgeService 负责事务与 checksum 去重
  → KnowledgeAiClient 调用 FastAPI
  → FastAPI 清洗正文、按句边界分块、生成本地向量
  → Spring Boot 使用 KnowledgeMapper 批量写入 MySQL
```

如果数据库中已经存在第二周导入的相同正文，但分块尚无向量，重复执行导入不会创建重复文档，而是按 `chunkIndex` 给旧分块回填向量。

### 2.2 基础 RAG 问答

```text
Vue 提问
  → POST /api/v1/chat/preview
  → ChatService 使用 MyBatis 加载带向量的候选分块
  → 可选 petType/category 在 MySQL 中先做元数据过滤
  → AiServiceClient 把问题与候选发送给 FastAPI
  → FastAPI 生成问题向量并计算余弦相似度
  → 按分数降序取 Top-K，并应用最低相关度阈值
  → 命中时生成 RAG 答案；未命中时进入通用模型模式
  → Vue 展示答案、来源标题和相关度
```

默认参数位于 `backend/business-service/src/main/resources/application.yml`：

| 配置 | 默认值 | 用途 |
|---|---:|---|
| `app.rag.candidate-limit` | `500` | MySQL 最多加载多少条已向量化候选 |
| `app.rag.top-k` | `3` | 最多保留多少条高分候选 |
| `app.rag.min-score` | `0.08` | 低于该余弦分数的候选不作为回答依据 |

Java 会把候选数量约束在 `1～2000`、Top-K 约束在 `1～10`，防止配置错误造成一次请求加载过多数据。

Java 调用 FastAPI 的默认响应超时为 35 秒，可通过 `AI_SERVICE_RESPONSE_TIMEOUT` 覆盖。该值应始终大于 FastAPI 的 `AI_LLM_TIMEOUT_SECONDS`（默认 20 秒），否则百炼仍在生成答案时 Java 会提前返回 502。

## 3. Java 标准分层结构

第三周重构后的主要结构如下：

```text
com.petassistant.business
├─ controller/               HTTP 入口、参数校验、状态码
│  ├─ ChatController
│  ├─ ConversationController
│  ├─ KnowledgeController
│  └─ SystemHealthController
├─ service/                  业务规则、事务、缓存和 RAG 编排
│  ├─ ChatService
│  ├─ ConversationService
│  ├─ ConversationCacheService
│  ├─ KnowledgeService
│  └─ InfrastructureHealthService
├─ client/                   FastAPI 外部调用
├─ config/                   MyBatis、HTTP 客户端、CORS 和配置对象
├─ exception/                业务异常与统一错误响应
└─ data/
   ├─ entity/                与数据库表对应的实体
   ├─ mapper/                标准 MyBatis Mapper 接口
   └─ dto/
      ├─ request/            浏览器请求对象
      ├─ response/           浏览器响应对象
      └─ internal/           Spring Boot 与 FastAPI 的内部契约

resources
└─ mapper/                   ConversationMapper.xml、KnowledgeMapper.xml
```

各层约束：

- Controller 不访问数据库，也不包含业务规则。
- Service 是业务和事务边界，只通过 Mapper 访问 MySQL。
- Client 只负责外部 HTTP 通信和错误转换。
- Entity 只描述持久化数据；HTTP DTO 不复用 Entity。
- Mapper 接口描述操作，具体 SQL 统一放在 XML，便于学习和检查。
- Flyway 继续管理表结构；MyBatis 只负责运行期数据读写。

## 4. 为什么使用标准 MyBatis

`pom.xml` 引入的是：

```xml
<dependency>
    <groupId>org.mybatis.spring.boot</groupId>
    <artifactId>mybatis-spring-boot-starter</artifactId>
    <version>3.0.5</version>
</dependency>
```

MyBatis 官方兼容说明中，`3.0` 系列支持 Spring Boot `3.2～3.5` 和 Java 17 及以上，符合本项目 Spring Boot 3.5 / Java 17 的组合。选择标准 MyBatis 而不是 MyBatis-Plus，是为了让 SQL、映射和动态条件都保持显式，便于理解查询究竟如何执行。

本项目采用“Mapper 接口 + XML SQL”：

- `ConversationMapper`：会话和消息的增删查。
- `KnowledgeMapper`：知识去重、批量写入、向量回填、列表和 RAG 候选查询。
- `@MapperScan`：在 `MyBatisConfig` 中统一扫描 Mapper。
- `map-underscore-to-camel-case`：数据库下划线字段自动适配 Java 驼峰字段。
- Java `record` 的基本类型构造器参数在 XML 中使用 `_int` 明确映射，避免 MyBatis 以 `Integer` 反射构造导致异常。

## 5. 数据库 V2 迁移

迁移文件：

`backend/business-service/src/main/resources/db/migration/V2__add_chunk_embeddings.sql`

它在 `knowledge_chunk` 增加：

| 字段 | 类型 | 说明 |
|---|---|---|
| `embedding_json` | `JSON` | 当前分块的向量数组 |
| `embedding_model` | `VARCHAR(100)` | 生成向量的模型或算法版本 |
| `embedding_dimensions` | `SMALLINT` | 向量维度，当前为 256 |
| `embedded_at` | `TIMESTAMP(6)` | 向量生成时间 |

同时创建 `(embedding_model, document_id)` 索引，用于快速过滤未向量化分块和指定模型的数据。

Spring Boot 启动时 Flyway 自动执行 V2。不要手工修改已经执行过的 V1 或 V2；未来结构变化应继续新增 V3、V4。

可以在 MySQL 中检查：

```sql
SELECT version, description, success
FROM flyway_schema_history
ORDER BY installed_rank;

SELECT id, document_id, chunk_index,
       embedding_model, embedding_dimensions, embedded_at
FROM knowledge_chunk;
```

## 6. 本地向量设计

### 6.1 为什么第三周不强制 API Key

第三周使用 `local-hash-zh-v1` 作为零网络依赖的基础向量算法：

1. 提取英文单词、中文单字和相邻中文二元词。
2. 使用 SHA-256 将每个 token 稳定映射到 256 个维度之一。
3. 对重复 token 使用对数频率权重。
4. 对向量执行 L2 归一化，使点积可作为余弦相似度。

它不是通用语义嵌入大模型，但具有确定性、无需下载模型、无需付费、可离线测试等优点，适合作为基础 RAG 的工程基线。后续替换为专业 embedding 模型时，只需更换 FastAPI 的向量服务并重新生成分块向量，Java/MyBatis 接口和知识主键可以保持不变。

### 6.2 为什么暂时把向量放 MySQL JSON

当前知识量很小，MySQL Community 没有在本项目中直接承担向量索引。第三周采用以下折中：

- MySQL 保存正文、元数据和 JSON 向量，是事实数据源。
- MySQL 先按状态、宠物类型、分类和数量限制筛候选。
- FastAPI 在内存中计算候选的余弦分数。

这种方式结构清楚、容易调试，适合数百到数千个小型分块；当知识库扩大后，应迁移到支持近似最近邻索引的向量数据库，而不是无限提高 `candidate-limit`。

## 7. 混合回答、来源与安全降级

FastAPI 的 `RagService` 支持两种模式。

### 7.1 默认：本地抽取式回答

未配置 API Key 时：

- 从最高分知识分块中切分完整句子。
- 计算问题 token 与句子 token 的重合度。
- 返回最相关句及相邻上下文。
- 附加“不能替代专业兽医诊断”的边界说明。

该模式的健康接口字段为：

```json
{
  "answer_mode": "local-extractive",
  "embedding_model": "local-hash-zh-v1"
}
```

这里的“默认”是指没有配置外部模型时。配置百炼后，命中知识库的回答会优先使用百炼组织语言。

### 7.2 阿里云百炼 API Key

项目直接识别阿里云官方推荐的 Windows 环境变量 `DASHSCOPE_API_KEY`。真实密钥不需要复制到项目文件，也不会写入日志或接口响应。

默认配置为华北 2（北京）共享兼容地址和 `qwen3.7-plus`：

```dotenv
AI_LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
AI_LLM_CHAT_MODEL=qwen3.7-plus
AI_LLM_TIMEOUT_SECONDS=20
```

如果 Key 属于其他地域、专属业务空间或 Coding Plan，需要在本机 `ai-service/.env` 覆盖与该 Key 匹配的 `AI_LLM_BASE_URL`；Base URL 与 Key 地域或计费方案不一致会导致 401。模型也可通过 `AI_LLM_CHAT_MODEL` 覆盖。

代码仍兼容原有 `AI_LLM_API_KEY`，但更推荐保留系统环境变量 `DASHSCOPE_API_KEY`。修改 Windows 环境变量后必须彻底重启 IDEA、CMD 和 FastAPI 进程，已经打开的程序不会自动获得新变量。

百炼调用成功时阶段为 `week-3-rag-llm`；调用失败时自动回退 `week-3-rag-local`，不会让整个问答接口失效。

重启 FastAPI 后访问 `http://localhost:8000/api/v1/ai/health`，配置生效时会看到：

```json
{
  "answer_mode": "compatible-llm",
  "llm_provider": "aliyun-bailian",
  "llm_model": "qwen3.7-plus"
}
```

健康接口只展示供应商与模型，不会返回 API Key。

### 7.3 可靠性边界

- 命中知识库且百炼成功时，返回 `week-3-rag-llm` 并附带实际来源。
- 未达到 `min-score` 且百炼可用时，进入 `week-3-general-llm`，来源为空并明确标记“未命中本地知识库”。
- 未命中且百炼未配置或调用失败时，返回 `week-3-rag-no-context` 并安全拒答。
- 本地回答成功时，阶段为 `week-3-rag-local`。
- 向量模型名或维度不一致的候选不会参与计算。
- 单条损坏的 JSON 向量会被 Java 跳过并记录警告，不影响其余候选。
- 同一资料召回多个分块时，页面来源只显示最高分的一条，避免重复来源。

通用模式只回答宠物饲养、护理和健康教育问题。涉及疫苗、用药、疾病或症状时，提示词要求模型说明答案依赖物种、年龄、地区和既往健康信息，不能做出诊断，并建议向当地兽医确认。

## 12. 常见问题

### 网页仍显示第二周或返回占位回答

Java、Python 和 Vue 都需要彻底停止旧进程后重新启动。只刷新网页不会让正在运行的后端加载新代码。

### `embeddedChunkCount` 为 0

说明该资料来自第二周或向量化导入未完成。确保 FastAPI 已启动，再重新执行样例导入脚本；相同 checksum 会走向量回填。

### 问答返回 `week-3-rag-no-context`

在混合模式中，这表示知识库未命中，而且百炼没有启用或调用失败。依次检查：

1. 知识列表是否至少有一条文档。
2. `embeddedChunkCount` 是否等于 `chunkCount`。
3. 请求中的 `petType/category` 是否与资料元数据一致。
4. `app.rag.min-score` 是否设置过高。
5. FastAPI 的 `AI_EMBEDDING_MODEL` 是否与数据库中的 `embedding_model` 一致。
6. `GET /api/v1/ai/health` 是否显示 `llm_provider=aliyun-bailian`。

如果返回 `week-3-general-llm`，说明百炼已经成功回答，但没有本地知识来源；这是混合模式的正常结果。

### 百炼已经配置，但网页等待约 10 秒后返回 502

这是 Java 等待 FastAPI 的时间短于百炼生成时间。第三周代码已将 `AI_SERVICE_RESPONSE_TIMEOUT` 默认设置为 `35s`，而 FastAPI 外部模型超时为 `20s`。更新代码后必须完全停止并重新启动 IDEA Java 中的 `BusinessServiceApplication`；只重启 FastAPI或刷新网页不会加载新的 Java 配置。

### 只有 Redis 显示 `DOWN`

Redis 仍只缓存会话摘要，不参与知识向量检索。缓存不可用时会话读取回退 MySQL，RAG 问答也可以继续运行；启动本机 Redis 后状态会恢复为 `UP`。

### 是否必须配置 API Key

不必须。第三周的本地向量、Top-K 检索、拒答、抽取式答案和来源展示都不需要 Key。配置 `DASHSCOPE_API_KEY` 后会自动启用百炼生成式回答；删除或暂时隐藏该变量后则继续使用本地模式。

## 13. 当前局限与第四周方向

当前版本已经是真实 RAG，不再是占位回答，但仍是教学型基线：

- 本地哈希向量主要依靠词面重合，通用语义召回能力不如专业 embedding 模型。
- MySQL JSON 没有近似最近邻索引，不适合直接扩展到大规模知识库。
- 本地抽取式回答适合可核对演示，不具备复杂综合、改写和多轮推理能力。
- 当前网页只负责问答和来源展示，知识上传管理页面尚未接入。
- 会话消息接口已经存在，但网页问答还没有完整绑定会话历史。

第四周建议完成：网页知识导入按钮、文档列表与导入进度、问答写入会话、多轮上下文、宠物档案过滤，以及更完整的业务异常提示。第五周再替换专业 embedding、建立固定评测集并优化召回参数。

## 15. 核心代码讲解（后补）

> 状态说明：第三周建立的 MyBatis、候选粗筛、Top-K 和来源返回结构继续使用；教学型 `local-hash-zh-v1` 已在第五周被 BGE 完整替代，生产代码中不再保留旧算法。

### 15.1 Mapper 接口和 XML 如何配对

Java Mapper 位于 `backend/business-service/src/main/java/com/petassistant/business/data/mapper/KnowledgeMapper.java`，SQL 位于 `src/main/resources/mapper/KnowledgeMapper.xml`。XML 的 `namespace` 必须等于接口全限定名，SQL 的 `id` 必须等于方法名。

```xml
<select id="findRagCandidates" resultMap="ragCandidateMap">
    SELECT c.id AS chunk_id,
           c.document_id,
           d.title,
           c.content,
           CAST(c.embedding_json AS CHAR) AS embedding_json,
           c.embedding_model,
           c.page_start,
           c.page_end
    FROM knowledge_chunk c
    INNER JOIN knowledge_document d ON d.id = c.document_id
    WHERE d.status = 'READY'
      AND c.embedding_json IS NOT NULL
    <if test="petType != null and petType != ''">
        AND d.pet_type = #{petType}
    </if>
    <if test="category != null and category != ''">
        AND d.category = #{category}
    </if>
    LIMIT #{limit}
</select>
```

MySQL 在这里负责状态、宠物类型和分类过滤，不在 SQL 中计算向量相似度。Java 把有限候选交给 FastAPI，FastAPI 才做真正余弦排序。这个分工适合当前小型知识库；候选达到数万时才需要迁移到专用向量数据库。

调试“明明有文档却没有候选”时依次检查：`status`、`embedding_json`、`pet_type`、`category` 和 `candidate-limit`。

### 15.2 Java 如何把 MySQL JSON 向量转换成内部 DTO

代码位置：`backend/business-service/src/main/java/com/petassistant/business/service/ChatService.java` 的 `deserializeCandidates()`。

```java
List<Double> embedding = objectMapper.readValue(
        row.embeddingJson(), EMBEDDING_TYPE
);
candidates.add(new AiRagCandidate(
        row.chunkId(), row.documentId(), row.title(),
        row.sourceName(), row.sourceUrl(), row.chunkIndex(),
        row.content(), embedding, row.embeddingModel(),
        row.fileName(), row.pageStart(), row.pageEnd()
));
```

数据库 JSON 在 Java 中先反序列化为 `List<Double>`，再通过内部 DTO 发送给 FastAPI。单条向量损坏会被跳过并记录 chunk ID，避免一条坏数据拖垮全部问答。第五周又加入 `embeddingModel` 校验，防止 512 维 BGE 与旧向量混排。

### 15.3 Top-K 排序真正发生在哪里

代码位置：`ai-service/app/services/rag_service.py` 的 `answer()`。

```python
query_vector = self.embedding_service.embed_query(
    self._build_retrieval_question(request)
)
ranked = []
for candidate in request.candidates:
    if candidate.embedding_model != self.embedding_service.model_name:
        continue
    score = self.embedding_service.cosine_similarity(
        query_vector, candidate.embedding
    )
    ranked.append((candidate, score))

ranked.sort(key=lambda item: item[1], reverse=True)
selected = [
    item for item in ranked if item[1] >= request.min_score
][:request.top_k]
```

执行顺序是：生成查询向量 → 排除模型版本不一致的候选 → 计算余弦相似度 → 降序 → 应用最低分 → 截取 Top-K。最低分和 Top-K 分别来自 Java 的 `app.rag.min-score` 与 `app.rag.top-k`。

调试检索时重点观察 `matching_model_count`、`max_score`、`selected`，而不是只看最终回答文本。

### 15.4 来源为什么由后端组装而不是模型编写

来源来自被选中的 `RagCandidate` 元数据，而不是让模型自由生成：

```python
sources.append(
    RagSource(
        title=candidate.title,
        url=candidate.source_url,
        chunk_id=candidate.chunk_id,
        score=round(score, 4),
        file_name=candidate.file_name,
        page_start=candidate.page_start,
        page_end=candidate.page_end,
    )
)
```

这保证标题、URL、分块 ID 和页码都能回到数据库记录。模型只负责答案正文，不能伪造引用。页面展示相关度时使用这里返回的 `score`。
