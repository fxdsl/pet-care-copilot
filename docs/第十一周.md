# 第十一周：社区知识共建、审核与可撤回 RAG

> 完成日期：2026-08-25  
> 数据库：Flyway V9，24 张业务表（不含 `flyway_schema_history`）  
> 核心技术：Spring Boot、MyBatis XML、FastAPI、RabbitMQ Outbox、Redis Hash/ZSet/Bloom/Lock/Stream、Vue 3  
> 本周原则：社区帖子绝不自动进入 RAG；AI 只辅助预检，最终发布必须人工批准。

## 1. 本周完成结果

第十一周把原来的“管理员填写表单 → 立即分块向量化 → READY”改造成了完整知识治理流程：

```text
社区帖子 / 管理员资料
  → MySQL 保存投稿与不可变版本快照
  → 同事务写 integration_outbox
  → RabbitMQ 独立知识队列
  → FastAPI 规则预检（隐私/广告/危险建议/Prompt Injection）
  → Redis ZSet 风险优先审核队列
  → 管理员对照原文与清洗文，人工批准/驳回
  → 批准后 RabbitMQ 异步清洗、分块、本地 Embedding
  → READY + APPROVED 文档进入 RAG
  → 作者撤回时文档改为 WITHDRAWN 并清缓存
```

已交付功能：

- 普通用户“知识共建”入口与四步投稿向导。
- 用户只能选择自己的已发布帖子，并必须勾选授权。
- 投稿版本、预检摘要、风险标签、质量分和审核时间线。
- 管理员资料上传不再绕过审核，支持 TXT/Markdown/文字型 PDF。
- 管理工作台统计卡片、状态/风险/来源筛选、风险优先队列。
- 审核抽屉中的原文/清洗文双栏对照、版本和时间线。
- A/B/C 信任等级；社区经验固定为 C，健康/疫苗内容禁止以 C 发布。
- RabbitMQ 异步预检与发布，MySQL 状态条件和 Redisson Lock 双重幂等。
- 撤回授权后文档立即退出 RAG；历史版本、审核和分块仍保留审计。
- V9 数据库迁移、数据库文档、README、路线图和自动化测试同步更新。

## 2. 为什么必须替换“直接导入”

旧入口 `POST /api/v1/knowledge/documents` 在一次请求里直接调用 FastAPI 并写入 `knowledge_document(status=READY)`。它无法回答以下问题：

- 谁授权了这段社区经验？
- 管理员审核的是哪一个版本？
- 原文是否包含隐私、广告或提示注入？
- 为什么批准或驳回？
- 作者撤回后怎样保证 RAG 不再召回？
- RabbitMQ 重复投递时会不会发布两次？

因此本周删除了旧 HTTP 入口、前端 `importKnowledge()`、`KnowledgeImportRequest/Response`、旧文档实体和旧 Mapper 写入语句。预处理输入改成内部 `KnowledgeProcessInput`，只能由审核发布服务和管理员重建任务调用。

删除前关键实现已经按约定归档到[第十周文档](第十周.md)“第十一周替换代码归档”。

## 3. 数据库 V9

迁移文件：`backend/business-service/src/main/resources/db/migration/V9__add_knowledge_submission_review_workflow.sql`。

### 3.1 三张新表

| 表 | 最终事实 | 关键唯一性/外键 |
|---|---|---|
| `knowledge_submission` | 当前投稿、授权、预检、审核、发布和错误状态 | `UNIQUE(source_type, source_business_id)`；作者/审核人删除置空 |
| `knowledge_submission_version` | 每次提交的不可变原文/清洗文快照 | `UNIQUE(submission_id, version)`；投稿删除级联 |
| `knowledge_review_record` | SUBMITTED 到 WITHDRAWN 的追加式时间线 | 投稿删除级联；审核人删除置空 |

状态机：

```text
PRECHECKING → PENDING_REVIEW → PUBLISHING → PUBLISHED
      │              └────────→ REJECTED
      └───────────────────────→ FAILED
作者可从可撤回状态 ───────────→ WITHDRAWN
```

`expectedVersion` 与 SQL 条件共同防止并发误审：

```xml
<update id="approve">
  UPDATE knowledge_submission
  SET status = 'PUBLISHING', reviewer_user_id = #{reviewerUserId}, reviewed_at = #{reviewedAt}
  WHERE id = #{id}
    AND current_version = #{expectedVersion}
    AND status = 'PENDING_REVIEW'
</update>
```

如果另一位管理员已经处理，影响行数为 0，Service 返回 `409 KNOWLEDGE_SUBMISSION_CONFLICT`。

### 3.2 `knowledge_document` 可检索条件

V9 增加来源、投稿、信任、授权、审核、版本、发布和有效期字段。Agent 候选 SQL 不只检查 READY：

```xml
WHERE d.status = 'READY'
  AND d.review_status = 'APPROVED'
  AND d.consent_status != 'WITHDRAWN'
  AND (d.expires_at IS NULL OR d.expires_at > CURRENT_TIMESTAMP(6))
  AND c.embedding_json IS NOT NULL
```

这道 SQL 是最终安全边界。即使 Redis 缓存没有及时删除，未审核、已撤回或过期资料也不能进入候选集。

## 5. 核心代码讲解

### 5.1 投稿和 Outbox 同事务

`submitCommunity()` 先用 `findOwnedView(postId, userId)` 验证帖子所有权与 `PUBLISHED` 状态，然后写主表、版本和审核记录：

```java
mapper.insertVersion(new KnowledgeSubmissionVersionEntity(
    UUID.randomUUID().toString(), submission.id(), submission.currentVersion(),
    submission.title(), submission.originalContent(), null, null,
    null, null, null, null, now
));
record(submission.id(), submission.currentVersion(), actorId,
       "SUBMITTED", null, "已提交预检");
outboxService.record("KNOWLEDGE_SUBMISSION", submission.id(),
                     "KNOWLEDGE_PRECHECK_REQUESTED", actorId);
```

三条记录处于同一 Spring 事务。MySQL 失败不会留下孤立 RabbitMQ 消息；RabbitMQ 暂时离线时 Outbox 保留 PENDING，恢复后继续发布。

### 5.2 FastAPI 免费、确定性的风险预检

预检接口不调用百炼通用模型，也不生成向量，因此不会消耗通用模型免费额度。它使用稳定规则识别：

- `PRIVACY`：手机号、邮箱、身份证样式。
- `ADVERTISEMENT`：加微、下单、代购、返现等。
- `PROMPT_INJECTION`：忽略系统指令、泄露提示词、越狱等。
- `DANGEROUS_ADVICE`：无需就医、随意停药、保证治愈等。
- `TOO_SHORT`：内容过短。
- `USER_EXPERIENCE`：社区经验来源标记。

```python
if re.search(r"(忽略.{0,12}(指令|规则)|system prompt|泄露提示词)", cleaned, re.I):
    labels.append("PROMPT_INJECTION")
risk_level = "HIGH" if high_labels.intersection(labels) else "MEDIUM" if labels else "LOW"
```

预检只辅助人工判断。高风险不会被自动批准；社区经验无论管理员请求什么等级，都由 Java 强制为 C。

### 5.3 RabbitMQ 路由隔离

`OutboxPublisher` 根据 `aggregateType` 选择交换机：

```java
boolean knowledgeEvent = "KNOWLEDGE_SUBMISSION".equals(event.aggregateType());
rabbitTemplate.convertAndSend(
    knowledgeEvent ? knowledgeExchange : communityExchange,
    knowledgeEvent ? knowledgeRoutingKey : communityRoutingKey,
    event.payloadJson(), message -> { ... }
);
```

社区媒体仍使用 `pet.community.events/pet.community.media`；知识使用 `pet.knowledge.events/pet.knowledge.workflow`，长时间向量任务不会阻塞媒体确认。

### 5.4 分布式发布幂等

批准只把状态改成 PUBLISHING 并写发布 Outbox。消费者发布时取得锁：

```java
RLock lock = redissonClient.getLock("knowledge:publish:" + submissionId);
locked = lock.tryLock(0, 90, TimeUnit.SECONDS);
KnowledgeSubmissionEntity submission = requireSubmission(submissionId);
if (!"PUBLISHING".equals(submission.status())) return;
String documentId = knowledgeService.publishApproved(submission, latestTrustLevel(submission.id()));
mapper.markPublished(submission.id(), submission.currentVersion(), documentId, Instant.now());
```

锁防止多个 Java 实例同时执行昂贵任务，MySQL `PUBLISHING + current_version` 是最终幂等条件。RabbitMQ 至少一次投递不会产生多份 READY 文档。

### 5.5 撤回不是物理删除

作者撤回时：

```java
mapper.withdrawOwned(submission.id(), userId, Instant.now());
knowledgeService.withdrawPublished(submission.id());
redisTemplate.delete("knowledge:document:" + submission.publishedDocumentId());
writeStream("WITHDRAWN", submission.id(), submission.publishedDocumentId(), submission.currentVersion());
```

文档状态变成 WITHDRAWN，保留原文、审核、分块和向量供审计；RAG SQL 立即排除。这样既满足撤回，又不会破坏历史审核证据。

## 6. Redis 数据结构

| Key | 类型 | 数据结构示例 | TTL/清理 | 回源/重建 |
|---|---|---|---|---|
| `knowledge:submission:{id}` | Hash | `status=PENDING_REVIEW, version=1, riskLevel=MEDIUM, updatedAt=...` | 15 分钟；状态变化清理或覆盖 | `knowledge_submission` |
| `knowledge:review:queue` | ZSet | member=投稿 ID，score=风险基数+创建毫秒 | 批准/驳回/撤回移除 | 按 `status=PENDING_REVIEW` 重建 |
| `knowledge:checksum:bloom` | Redisson Bloom | SHA-256 checksum | 可重建 | 最终仍查 MySQL 唯一 checksum |
| `knowledge:publish:{id}` | Redisson Lock | 无业务正文 | 90 秒租约 | MySQL 状态二次校验 |
| `knowledge:index:events` | Stream | type/submissionId/documentId/version/occurredAt | 近似 MAXLEN 10000 | 投稿和文档表 |
| `knowledge:document:{id}` | String JSON 摘要 | READY、submissionId、version | 6 小时；撤回主动删 | `knowledge_document` |

风险排序：HIGH 基数 0、MEDIUM 基数 `1e12`、LOW 基数 `2e12`，同风险内按创建时间先来先审。

## 7. HTTP 接口完整契约

所有 Spring Boot 接口要求 `Authorization: Bearer <accessToken>`。普通投稿接口仅 `USER/VERIFIED_SELLER`；管理接口仅 `ADMIN`。

### 7.1 POST `/api/v1/knowledge-submissions/community`

用途：把当前用户自己的已发布帖子提交知识审核。

Path/Query：无。

Body：

| 字段 | 类型 | 必填 | 约束/含义 |
|---|---|---:|---|
| `postId` | string | 是 | 当前用户自己的 PUBLISHED 帖子 ID |
| `petType` | string | 是 | `CAT/DOG/OTHER` |
| `category` | string | 是 | `FEEDING/HEALTH/VACCINE/BEHAVIOR/GROOMING/OTHER` |
| `consentGranted` | boolean | 是 | 必须为 true |

示例：

```json
{"postId":"post-uuid","petType":"CAT","category":"FEEDING","consentGranted":true}
```

成功：`201`，返回完整 `KnowledgeSubmissionResponse`，初始 `status=PRECHECKING`、`consentStatus=GRANTED`、`currentVersion=1`。

错误：`400 INVALID_REQUEST`（非本人/非已发布、枚举无效、未授权）；`401` 未登录；`403` 角色不允许；`409 KNOWLEDGE_SUBMISSION_CONFLICT`（同一帖子已有进行中投稿）。

Query：

| 参数 | 类型 | 默认 | 范围 |
|---|---|---|---|
| `page` | int | 0 | 小于 0 归一为 0 |
| `size` | int | 20 | 1～50 |

成功 `200`：

{"items":[{"id":"...","title":"幼猫经验","status":"PENDING_REVIEW","timeline":[]}],"page":0,"size":20,"total":1}

Path：`submissionId`。Query/Body：无。

成功 `200`：返回更新后的投稿，`status=WITHDRAWN`、`consentStatus=WITHDRAWN`。若已发布，对应文档同步变为 WITHDRAWN。

Body：

该接口由 Java 消费者内部调用，浏览器不直接调用。

## 8. 前端交互

### 8.1 普通用户

导航新增“知识共建”，地址 `/app/knowledge`。投稿向导四步分别阻止以下错误：

1. 未选择已发布帖子不能下一步。
2. 展示当前帖子快照，提醒之后编辑不会改变正在审核版本。
3. 未勾选授权不能下一步。
4. 提交后显示 PRECHECKING，不伪装成已经入库。

右侧投稿列表展示状态和版本；详情区展示风险、质量分和时间线；撤回按钮会真实调用 DELETE 接口。

### 8.2 管理员

原“导入资料”卡片已替换为治理工作台：

- 顶部：待审核、高风险、已发布、已驳回统计。
- 左侧：来源机构、作者、链接、日期、有效期和正文登记。
- 右侧：状态/风险/来源筛选和风险优先审核队列。
- 抽屉：原文与清洗文对照、风险标签、摘要、质量分、审核时间线、A/B/C 和原因。
- 底部：已发布 READY 文档列表与独立 RAG 验证。

## 9. 错误处理与恢复

| 故障 | 用户看到 | 数据状态 | 恢复方式 |
|---|---|---|---|
| RabbitMQ 未启动 | 投稿创建成功但停在 PRECHECKING/PUBLISHING | Outbox 保持 PENDING/FAILED 重试时间 | 启动 RabbitMQ，OutboxPublisher 继续投递 |
| FastAPI 未启动 | 异步消费者把投稿标为 FAILED | 审核记录追加 FAILED，原文不丢 | 启动 FastAPI；当前可重新提交社区版本，管理员资料可重新登记 |

| Redis 未启动 | 缓存/排序/Bloom/Stream 跳过 | MySQL 投稿、审核、发布仍是事实；发布锁不可用时任务失败可观察 | 启动 Redis 后重新处理；审核列表始终可查 MySQL |
| 两位管理员同时审核 | 一方成功，另一方 409 | 只产生一条有效状态变化 | 刷新详情后查看最新 timeline |
| RabbitMQ 重复消息 | 无重复页面结果 | 状态条件与 Redisson Lock 幂等 | 无需人工处理 |
| 作者撤回 | 页面显示 WITHDRAWN | 文档和授权均 WITHDRAWN | 如需再次投稿，重新提交产生新版本 |

## 10. 启动与人工验收

启动顺序：MySQL → Redis → RabbitMQ → FastAPI 8000 → Spring Boot 8080 → Vue 5173。

RabbitMQ 本机脚本：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File G:\develop\start-rabbitmq.ps1
```

使用内置“幼猫基础喂养”样例时，先以管理员登录并从浏览器 Network 或登录响应复制 `accessToken`，再在项目根目录执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\import-sample-knowledge.ps1 -AccessToken "你的管理员AccessToken"
```

也可以把 Token 只放在当前终端环境变量中，避免进入 PowerShell 命令历史：

```powershell
$env:PET_ASSISTANT_ADMIN_TOKEN = "你的管理员AccessToken"
.\scripts\import-sample-knowledge.ps1
```

脚本调用 `POST /api/v1/admin/knowledge-submissions/uploads`，成功只表示创建 `PRECHECKING` 投稿，不代表已经进入 RAG；管理员仍需在工作台检查并批准。脚本不会读取或保存百炼 API Key。

验收步骤：

1. 普通用户发布一篇非医疗社区帖子。
2. 打开“知识共建”，选择帖子、确认正文和授权后提交。
3. 确认状态先为 PRECHECKING，RabbitMQ/FastAPI 正常后变 PENDING_REVIEW。
4. 管理员打开知识库工作台，查看风险标签和原文/清洗文。
5. 批准 FEEDING 社区经验，确认状态先 PUBLISHING 后 PUBLISHED。
6. 在底部 RAG 测试中提问，确认能看到实际来源。
7. 用户撤回投稿，再次提问确认该文档不被召回。
8. 提交带手机号或“忽略系统指令”的文本，确认风险 HIGH，非 A 级不能批准。
9. 两个管理窗口同时审核同一版本，确认只有一个成功，另一个返回 409。
10. 查看 `knowledge_review_record`，确认 SUBMITTED、PRECHECK_COMPLETED、APPROVED、PUBLISHED/WITHDRAWN 完整存在。
