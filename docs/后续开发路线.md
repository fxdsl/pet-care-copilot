# 后续开发路线：宠物社区、知识共建与内容发现

## 1. 文档定位

本文记录第七周及以后的开发安排，目标是把现有“宠物智能问答助手”扩展为：

> AI 驱动的宠物社区 + 宠物档案 + 知识共建 + 智能内容发现平台。

本文是**规划文档**，其中功能、表、Redis Key 和中间件均未视为已经实现。为了避免规划路径与最终代码不一致，本文不提前声明 HTTP 接口地址。每一周真正完成后，必须在对应的“第几周”文档中补全全部接口的 Path、Query、Body、嵌套字段、响应字段、错误码和请求/响应示例。

规划原则：

- 先完善用户、权限和内容治理，再开放社区知识收录、统一搜索和个性化推荐。
- MySQL 始终是真实数据源；Redis 用于缓存、计数、排行、限流、地理位置、事件和并发控制，不能代替持久化数据库。
- 保持 Spring Boot 模块化单体，业务稳定后再决定是否拆分微服务。
- 新实现替换旧实现时删除失效的生产代码；大规模删除的核心实现归档到上一周开发文档。
- 所有新增代码写说明性注释，Java 继续使用 `controller/service/data/mapper` 分层和 MyBatis XML。
- `ADMIN` 不默认继承普通养宠用户的页面和业务能力；前端导航、路由守卫和后端接口授权必须同时按角色隔离，不能只隐藏按钮。
- 涉及宠物健康、隐私、内容审核的功能必须默认采用更严格的权限和审核策略。

## 2. 目标页面与业务模块

后续前端主导航规划为：

| 模块 | 面向用户的核心能力 |

| 消息中心 | 私信、评论/点赞/关注通知、审核结果和系统通知 |

### 2.1 前端现状与必须先解决的问题

截至 2026-08-22，前端功能链路已经可用，但仍属于教学原型：`frontend/src/App.vue` 有 1034 行、约 47 KB，登录、问答、宠物档案、社区和管理页面集中在一个组件中；`styles.css` 有 952 行；依赖中只有 Vue，没有正式路由、全局状态管理和 UI 组件库。继续在这个文件上叠加评论、消息、搜索和推荐，会造成页面状态互相干扰、无法通过 URL 直达、重复样式越来越多，也不利于移动端适配和自动化测试。

因此，前端优化不是第十四周才做一次“换肤”，而是从第九周开始贯穿每一周：第九周先完成架构、设计令牌和社区首页，第十至十三周在新增业务时同步交付对应的成熟页面，第十四周再做全站一致性、性能、无障碍和视觉回归验收。

### 2.3 前端技术与视觉方案

- 使用 [Vue Router](https://router.vuejs.org/) 建立真实 URL、路由守卫、404 页面和滚动恢复；各页面采用动态导入，访问时再加载对应代码块。
- 使用 [Pinia](https://pinia.vuejs.org/introduction.html) 管理当前用户、权限、未读数、筛选条件和跨页面草稿；服务端业务数据仍由 API 获取，不把 Pinia 当数据库。
- 管理端和复杂表单按需使用 [Element Plus](https://element-plus.org/en-US/guide/installation.html) 的表格、分页、表单、对话框、抽屉、上传、提示和骨架屏；普通用户端保留“宠里个宠”的自有卡片与色彩，避免全站变成通用后台模板。
- 建立颜色、字体、字号、间距、圆角、阴影、层级和动效时长等 CSS Design Tokens；页面只能消费令牌，不再散落相近但不同的颜色和间距。
- 普通用户使用顶部导航 + 移动端底部导航；管理员使用独立侧栏 + 顶栏布局。两者共享登录态、基础按钮、反馈、头像和空状态组件，但不共享不合适的业务布局。
- 统一实现 `loading / skeleton / empty / error / forbidden / offline` 六类状态，以及 Toast、确认框、表单字段错误、重试按钮和危险操作二次确认。
- 图片使用固定宽高比容器、懒加载、占位和失败回退；帖子详情支持媒体预览，列表避免原图撑开导致页面抖动。
- 键盘可完成导航、表单和弹窗操作；焦点可见；颜色不能成为唯一状态表达；普通文字对比度目标至少 4.5:1。

## 3. 总体技术边界

### 3.1 Java 模块规划

在现有工程内按业务模块组织，模块内部仍保持标准分层：

```text
com.petassistant.business
├─ auth/          用户、登录、令牌和权限
├─ pet/           宠物档案与归属关系
├─ community/     帖子、话题和媒体
├─ social/        点赞、评论、收藏、关注和推荐
├─ moderation/    举报、审核、敏感内容和申诉
├─ knowledge/     资料导入、知识投稿、版本和发布
├─ search/        帖子、知识、用户和话题的统一检索
├─ recommendation/ 推荐候选、排序解释和用户反馈
├─ message/       私信、站内通知和未读数
└─ ai/            Agent 编排、RAG、模型调用与执行审计
```

每个模块根据需要建立 `controller`、`service`、`data/dto`、`data/entity`、`data/mapper`；SQL 继续放在 `resources/mapper`。实体、请求 DTO、响应 DTO 和内部 DTO 不混放。

### 3.2 暂不拆微服务

第七至第十四周采用模块化单体，RabbitMQ、Redis、MinIO 和 OpenSearch 作为独立基础设施。当前阶段不引入 Dubbo、Nacos 或 Kafka，也不为了展示技术栈而拆分空壳服务。只有出现明确的独立扩容、独立发布或团队边界时，才评估拆分。

### 3.3 数据一致性

- MySQL 保存用户、帖子、评论、审核、知识、关系、推荐反馈和消息的最终状态。
- Redis 缓存失败时允许回源 MySQL；关键写入不能只写 Redis。
- 计数类数据可以先写 Redis，但必须通过消息队列或定时任务可靠回写 MySQL。
- 跨模块异步事件采用 Outbox 方案：业务数据和事件记录同一 MySQL 事务提交，再投递 RabbitMQ。
- 每个写接口都要定义幂等键、事务边界和重复请求行为。

## 5. 第七周：用户、认证、权限和宠物归属

> 完成状态：已于 2026-08-21 实现并验收，真实代码、接口参数和测试结果见[《第七周》](第七周.md)。

### 5.1 功能范围

- 用户注册、登录、退出、访问令牌刷新和密码修改。
- 用户头像、昵称、简介、地区等基础资料。
- 宠物档案必须归属于当前登录用户，查询和修改均做所有权校验。
- 角色初步划分为 `USER`、`VERIFIED_SELLER`、`MODERATOR`、`ADMIN`。
- 管理端与普通用户端使用同一权限模型，不在 Controller 写散落的角色判断。

### 5.2 Redis 实践

- `auth:refresh:{tokenId}`：String，保存刷新令牌会话，设置明确 TTL。
- `auth:login:fail:{account}`：String 计数，连续失败后短时冻结。
- `auth:rate:{ip}:{action}`：Lua 原子令牌桶，限制登录、注册和验证码频率。
- `user:session:{userId}`：Hash，缓存会话摘要，不存密码和完整敏感资料。
- 使用 Redisson Lock 保护同一刷新令牌并发换取新令牌，旧令牌旋转后立即失效。

### 5.3 验收标准

越权读取或修改他人宠物档案必须失败；退出后刷新令牌不可再次使用；Redis 停止时只允许安全降级，不能绕过登录或权限检查。对应周文档要完整解释 Security Filter Chain、JWT 校验、MyBatis 所有权 SQL、Redis Key 与接口参数。

### 5.4 已识别改进项（排入第八周）

第七周实现了角色鉴权，但当前前端采用“普通用户导航 + 管理员额外入口”的叠加方式，因此纯管理员仍能看到智能问答和宠物档案。这不符合系统管理员的实际工作边界，第八周先完成以下补强：

- 为普通用户和管理员生成独立导航与路由；管理员只保留账号设置、知识库、用户治理、内容审核、日志和系统状态。
- 宠物档案和普通智能问答在后端也限制为普通养宠用户角色，不能只靠 Vue 隐藏入口。
- 在知识库管理页提供管理员专用的检索、召回来源和模型回答测试，不写入普通问答会话，也不要求宠物档案。
- 增加管理员用户管理：查询用户、提升/撤销角色、禁用/恢复账号，并禁止撤销系统中的最后一个 `ADMIN`。
- 角色或状态修改必须记录操作者、目标用户、修改前后值和时间，并立即撤销目标用户刷新令牌、失效用户缓存和旧权限凭证。
- 引导变量只保留为灾难恢复和首次初始化手段；日常创建管理员改由受保护的管理后台完成。

## 6. 第八周：宠物社区发布与媒体

> 完成状态：已于 2026-08-22 实现并验收。角色门户、管理员治理、社区帖子、MinIO 预签名上传、Outbox/RabbitMQ 通道、Redis 缓存/计数/Bloom 和完整接口参数见[《第八周》](第八周.md)。当前异步消费者完成媒体确认事件的幂等状态闭环；真正的图片缩略图、视频转码和内容模型初筛仍需专用处理器，随第九至十一周内容治理继续实现。

### 6.1 功能范围

- 普通用户门户只展示 AI 问答、宠物档案、社区和个人中心；管理员门户只展示知识、用户、审核、审计和系统管理。
- 增加管理员用户列表、条件查询、角色调整、账号禁用/恢复和权限变更审计；所有写操作必须校验操作者仍为 `ADMIN`。
- 增加知识库“检索/回答测试”工作台，展示召回片段、相似度、模型名称和最终答案，但不污染普通会话历史。
- 前端路由守卫只负责体验，Spring Security 和 Service 层继续执行真实权限与业务规则校验。
- 帖子草稿、发布、编辑、删除、详情和用户主页列表。
- 帖子可关联一个宠物档案、话题、地区和多张图片或短视频。
- 媒体先获得受限上传凭证，上传完成后由后端确认归属和文件类型。
- 帖子状态至少包含草稿、待审核、已发布、已隐藏、已删除。

### 6.2 Redis 与中间件

- MySQL 为用户角色、状态和 `security_version` 的真实来源；JWT 携带安全版本，Redis 缓存当前版本，角色撤销或禁用时递增版本并让旧访问令牌立即失效。
- 角色/状态变化后删除 `user:session:{userId}`，撤销该用户全部 `auth:refresh:*` 会话；Redis 不可用时权限校验必须安全失败或回源 MySQL，不能沿用旧权限。
- `community:post:{postId}`：Hash 或序列化对象，缓存已发布帖子详情。
- 更新帖子时先提交 MySQL，再删除缓存；读取采用 Cache-Aside。
- `community:post:counter:{postId}`：Hash，聚合浏览、点赞、评论和收藏数。
- Bloom Filter 判断明显不存在的帖子 ID，防止缓存穿透；最终仍以 MySQL 为准。
- MinIO 保存媒体文件，MySQL 保存对象 Key、类型、大小、校验和和业务归属。
- RabbitMQ 先可靠承载媒体确认/发布事件和幂等处理状态；缩略图、转码与内容初筛由后续专用消费者接入。Redis 浏览增量由 Lua + 定时任务可靠回写 MySQL。

### 6.3 验收标准

### 9.2 收录工作流

```text
帖子/管理员资料
  → 作者授权与来源登记
  → 隐私、广告、违法、危险建议和 Prompt Injection 初筛

```

AI 只做辅助审核，不能自动批准高风险医疗、用药、疫苗或身份资质内容。社区正文一律作为“不可信数据”送入模型，文中要求模型忽略规则、泄露系统提示词或调用工具的内容不得执行。

### 9.3 信任分级

| 等级 | 来源 | 使用规则 |
|---|---|---|
| A | 官方机构、管理员核验的专业资料 | 可作为高风险问题的主要来源，但仍提示咨询兽医 |
| B | 认证兽医/专业人员且通过审核的内容 | 可作为主要或补充来源，展示作者资质和审核时间 |
| C | 普通用户审核通过的养宠经验 | 仅用于喂养体验、行为、用品等低风险补充，不作为诊断依据 |

### 10.1 功能范围

- 建立独立搜索页，统一检索已公开的社区帖子、已发布知识、用户和话题。

- 私密资料、未审核知识、已删除或被屏蔽的内容不能写入公开索引，也不能通过搜索接口绕过权限。

### 10.2 索引工作流

```text
MySQL 业务事务
 → 同事务写入 Outbox 事件
 → RabbitMQ 投递索引新增/更新/删除事件
 → 幂等消费者读取最新业务状态
 → 写入或删除 OpenSearch 查询副本
 → 前端搜索并按权限二次过滤
```

OpenSearch 只保存搜索所需的脱敏字段，MySQL 始终是最终事实来源。索引异常时可以停止增量消费并从 MySQL 全量重建，重建过程不得反向修改业务表。

### 10.3 检索与 Redis 实践

- BM25 负责宠物品种、疾病名称、话题和用户名等精确词匹配。
- 本地向量负责语义相似召回，最终使用可解释权重混合重排。
- String/Hash + TTL：缓存热门查询和第一页结果摘要；索引版本变化后主动失效。
- ZSet：统计脱敏后的搜索热词和内容发现趋势，不保存原始敏感查询。
- Bloom Filter：快速判断明显不存在的公开业务 ID，最终存在性仍由 MySQL 确认。
- Lua：限制同一用户/IP 的搜索联想和高频复杂查询。
- Redisson Lock：保证同一索引版本只有一个全量重建任务。

### 10.4 验收标准

新增、修改、删除和审核状态变化能最终反映到索引；重复消息不会生成重复文档；未授权内容无法搜索；OpenSearch 清空后能从 MySQL 重建；Redis 停止时允许降级直查搜索服务，但不能放宽权限。搜索页面必须展示结果类型、命中字段和来源，不能把知识资料与普通经验混为同一可信等级。

- MySQL 事务通过 Outbox + RabbitMQ 发布互动、内容变更、关系变更和推荐反馈事件，消费者必须按事件 ID 幂等。

- 定时任务使用数据库租约或分布式锁避免多实例重复执行，但最终结果仍由 MySQL 唯一约束和状态条件保护。

### 11.3 Redis 实践

- Set：屏蔽、拉黑、已关注和“不感兴趣”关系的快速过滤，MySQL 保存最终关系。
- ZSet：推荐候选、热门内容和用户活跃度的带时间衰减排序。
- Stream：记录可重放的推荐反馈和治理任务进度；消费组负责确认、重试和积压监控。
- Hash + TTL：缓存推荐解释和用户候选摘要，关系变化后主动失效。
- Redisson Lock：保护趋势快照、索引补偿和同一批次推荐重建。

## 13. Redis 用法总表

| Redis 能力 | 项目落点 | 不能承担的职责 |
|---|---|---|
| String + TTL | 令牌、验证码、失败次数、在线状态、幂等结果 | 永久用户或内容数据 |
| Hash | 帖子/搜索摘要、未读数、任务进度、审核摘要 | 无审计的最终业务状态 |
| Set | 点赞、收藏、关注关系 | 仅靠 Redis 判定永久关系 |
| ZSet | 热门榜、信息流、审核队列、超时优先级 | 精确且永久的业务排序 |
| GEO | 附近帖子和同城内容 | 保存精确家庭地址 |
| Bitmap | 签到、喂养/喂药打卡 | 复杂记录详情 |
| HyperLogLog | 页面 UV 和趋势 | 精确人数或权限判断 |
| Stream | 通知、知识索引、推荐反馈的消费与重放 | 替代全部业务消息表 |
| Pub/Sub | 在线即时广播 | 离线可靠通知 |
| Lua | 原子限流、计数和关系变更 | 绕过 MySQL 约束 |
| Bloom Filter | 帖子/用户/知识 ID 与内容校验和快速判空 | 最终存在性和去重结论 |
| Redisson Lock | 令牌刷新、趋势快照、重建索引和幂等任务 | 数据库事务与唯一索引 |

Redis Key 统一使用 `业务:对象:标识[:维度]`；所有缓存必须写明 TTL、失效时机、回源策略、重建方式和 Redis 不可用时的行为。参考：[Redis 数据类型](https://redis.io/docs/latest/develop/data-types/)、[Spring Data Redis Streams](https://docs.spring.io/spring-data/redis/reference/redis/redis-streams.html)、[Redisson 锁](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/)。
