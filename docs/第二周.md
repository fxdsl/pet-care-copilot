## 1. 本周目标与完成情况

第二周把第一周的“三端可通信骨架”推进为可保存业务数据、可导入知识资料的数据基础版本。本周已完成：

2. 使用 Flyway 管理数据库结构，Spring Boot 启动时自动检查并执行迁移。
3. 实现会话与消息 REST API，并给会话摘要增加 Redis 缓存。
4. Redis 不可用时自动回退 MySQL，避免缓存故障拖垮主业务。
5. 在 FastAPI 实现知识文本清洗、SHA-256 去重标识和带重叠的分块。
6. 实现 Spring Boot → FastAPI → MySQL 的知识导入链路。
7. 提供一份幼猫喂养样例和一键导入脚本。
8. 扩展聚合健康检查，使 MySQL、Redis、FastAPI 状态可直接观察。

本周仍不会生成真正的 RAG 答案。原因是知识分块虽然已经入库，但尚未生成向量，也没有执行相似度检索；这是第三周的任务。

## 2. 架构与数据流

### 2.1 服务职责

```text
Vue 3（5173）
    │ 只访问业务层
    ▼
Spring Boot（8080）
    ├─ MySQL（3306）：持久化业务数据和知识内容
    ├─ Redis（6379）：缓存会话摘要
    └─ FastAPI（8000）：清洗和切分知识文本
```

- Spring Boot 是唯一业务入口，负责参数校验、事务、去重和数据持久化。
- FastAPI 负责适合 Python 生态的文本预处理，将来继续承载向量化、RAG 和 Agent。
- MySQL 是事实数据源；Redis 只保存可重新计算的缓存。

### 2.2 知识文档导入过程

```text
导入请求
  → Spring Boot 校验元数据和分块参数
  → FastAPI 统一换行、空格和空行
  → FastAPI 按句子边界生成带重叠分块
  → FastAPI 对清洗后的全文计算 SHA-256
  → Spring Boot 按 checksum 判断是否已经导入
  → 新文档和全部分块在同一个 MySQL 事务中写入
```

同一份清洗后内容重复导入时不会产生第二份数据，响应中的 `created` 为 `false`。

### 2.3 会话缓存过程

读取 `GET /api/v1/conversations/{id}` 时：

1. 先读 Redis 键 `pet-assistant:conversation:{id}`。
2. 命中时返回摘要，响应 `source` 为 `REDIS`。
3. 未命中时查询 MySQL、写入 Redis，再返回，`source` 为 `MYSQL`。
4. 添加新消息后删除对应缓存，防止 `messageCount` 过期。
5. Redis 连接失败时捕获异常并直接访问 MySQL，接口仍可正常工作。

默认缓存有效期为 30 分钟，可通过 `app.cache.conversation-ttl` 修改。

## 3. 数据库设计

迁移文件位于：

`backend/business-service/src/main/resources/db/migration/V1__create_business_and_knowledge_tables.sql`

| 表名 | 作用 | 关键约束 |
|---|---|---|
| `app_user` | 用户基础信息 | `username` 唯一 |
| `conversation` | 会话主体 | 可关联用户；删除用户时保留会话 |
| `message` | 多轮消息 | 关联会话；角色只能为 `USER/ASSISTANT/SYSTEM/TOOL` |
| `knowledge_document` | 清洗后的知识全文及元数据 | `content_checksum` 唯一，避免重复文档 |
| `knowledge_chunk` | 文档分块 | 同一文档的 `chunk_index` 唯一 |
| `answer_feedback` | 用户对回答的反馈 | 每条消息最多一份反馈，评分为 `-1` 或 `1` |

全部表使用 InnoDB、`utf8mb4` 和外键。知识分块暂时不含向量列，因为第三周会根据选定的向量存储方案补充。

### 为什么使用 Flyway

只手工建表很难保证每台机器结构一致。Flyway 会记录已经执行的版本：

- 第一次启动执行 `V1` 并创建业务表。
- 后续启动只校验，不重复执行。
- 修改结构时新增 `V2__说明.sql`，不要改已经在数据库执行过的 `V1`。

可在 MySQL 的 `flyway_schema_history` 表查看迁移记录。

### 6.4 FastAPI 预处理接口

通常由 Spring Boot 内部调用，不建议前端直接访问：

```http
POST /api/v1/knowledge/preprocess
```

处理规则：

- 移除 UTF-8 BOM 和不间断空格。
- 将 Windows/旧 Mac 换行统一为 `\n`。
- 合并行内连续空格，连续空行最多保留一个。
- 优先在中文句号、问号、感叹号、分号或换行后切分。
- 找不到合适句子边界时按最大字符数切分。
- 相邻分块保留重叠文本，为后续检索保留语义上下文。
- 使用清洗后全文的 SHA-256 作为稳定去重标识。

默认 `chunkSize=800`、`chunkOverlap=120`；重叠长度必须小于分块大小。

## 9. 常见问题

### Spring Boot 报 `Unknown database 'pet_assistant'`

先执行第 4.2 节的 `CREATE DATABASE`。Flyway 只能在已有数据库中创建表，不负责创建数据库本身。

### Spring Boot 报 MySQL 认证失败

检查 `backend/business-service/.env` 的用户名和密码，并确认 IDEA Working directory 指向该目录。不要把真实密码写进 `.env.example`。

### 健康检查只有 Redis 为 `DOWN`

表示 Redis 未监听 `6379`。可以启动 Redis；如果当前只验证知识导入和 MySQL，会话接口仍能正常工作。

### 知识导入返回 `502 AI_SERVICE_UNAVAILABLE`

先打开 `http://localhost:8000/api/v1/ai/health`。打不开时说明 FastAPI 未启动或端口与 `AI_SERVICE_BASE_URL` 不一致。

### FastAPI 健康检查为 `UP`，但问答仍返回 `502`

如果直接调用 FastAPI 的 POST 成功、只有 Spring Boot 转发失败，需要确认 Java 客户端使用 HTTP/1.1。项目已在 `WebClientConfig` 中固定 `HttpClient.Version.HTTP_1_1`，用于避免 JDK HttpClient 对 Uvicorn 的 HTTP/2 明文升级兼容问题。更新代码后必须彻底停止 IDEA 中原来的 Java 进程，再重新运行 `BusinessServiceApplication`；只刷新网页不会加载新代码。

### 重复导入后为什么 `created=false`

这是 checksum 去重生效。同一份内容即使标题相同或不同，只要清洗后的正文完全一致，就复用现有文档。

### 10.1 第三周 Java 包结构约定

第三周重构后的目标结构如下：

```text
com.petassistant.business
├─ controller/              HTTP 接口、参数校验和状态码
├─ service/                 业务编排、事务和缓存策略
├─ client/                  FastAPI 等外部服务客户端
├─ data/
│  ├─ entity/               与数据库表对应的实体
│  ├─ dto/
│  │  ├─ request/           接口请求对象
│  │  └─ response/          接口响应对象
│  └─ mapper/               MyBatis Mapper 接口
├─ config/                  Spring、MyBatis、跨域和客户端配置
├─ exception/               业务异常与统一异常处理
└─ common/                  少量真正可复用的公共类型

resources
└─ mapper/                  MyBatis XML 映射文件
```

执行约束：

- Controller 不直接访问 Mapper，也不编写业务规则。
- Service 是事务边界，通过 Mapper 访问数据。
- 数据库实体统一放在 `data/entity`，不与 Controller 或 Service 写在同一文件。
- 请求和响应 DTO 与数据库实体分离，避免接口字段变化直接影响表映射。
- Mapper 接口放在 `data/mapper`，复杂 SQL 放在 `resources/mapper/*.xml`。
- 外部 FastAPI 调用放在 `client`，不混入 Service 或 Controller。
- 统一异常处理放在 `exception`，配置类继续放在 `config`。

## 11. 核心代码讲解（后补）

> 状态说明：第二周最初的 Redis 会话摘要已在第五周删除并迁移为“最近 12 条模型上下文缓存”。Flyway V1 数据表仍是当前数据库基础，不能删除。

### 11.1 Flyway V1 如何保证会话消息顺序

代码位置：`backend/business-service/src/main/resources/db/migration/V1__create_business_and_knowledge_tables.sql`。

```sql
CREATE TABLE message (
    id CHAR(36) NOT NULL,
    conversation_id CHAR(36) NOT NULL,
    role VARCHAR(20) NOT NULL,
    content TEXT NOT NULL,
    model_name VARCHAR(100) NULL,
    created_at TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    KEY idx_message_conversation_created (conversation_id, created_at),
    CONSTRAINT fk_message_conversation
        FOREIGN KEY (conversation_id) REFERENCES conversation (id) ON DELETE CASCADE,
    CONSTRAINT chk_message_role
        CHECK (role IN ('USER', 'ASSISTANT', 'SYSTEM', 'TOOL'))
);
```

关键点不是语法本身，而是三个约束：

1. `conversation_id` 把每条消息绑定到唯一会话。
2. 联合索引支持按会话和时间读取历史。
3. 外键级联删除避免会话删除后留下孤儿消息。

`role` 从一开始就预留了 `TOOL`，第六周 Agent 工具消息可以沿用，不需要修改旧迁移文件。调试消息缺失时，先按 `conversation_id` 查询 `message` 表，再检查事务是否回滚。

### 11.2 为什么知识文档和分块分成两张表

同一 V1 中，`knowledge_document` 保存来源、分类和完整正文，`knowledge_chunk` 保存可检索的小段：

```sql
CREATE TABLE knowledge_chunk (
    id CHAR(36) NOT NULL,
    document_id CHAR(36) NOT NULL,
    chunk_index INT NOT NULL,
    content TEXT NOT NULL,
    char_count INT NOT NULL,
    token_estimate INT NOT NULL,
    UNIQUE KEY uk_knowledge_chunk_order (document_id, chunk_index),
    CONSTRAINT fk_knowledge_chunk_document
        FOREIGN KEY (document_id) REFERENCES knowledge_document (id) ON DELETE CASCADE
);
```

完整文档适合管理和重建，分块适合检索和引用。`(document_id, chunk_index)` 唯一约束保证一个文档不会出现两个相同序号的分块。第三、第五周只给分块增加向量和页码，没有破坏第二周的数据边界。

### 11.3 MyBatis 如何按时间恢复完整历史

代码位置：`backend/business-service/src/main/resources/mapper/ConversationMapper.xml`。

```xml
<select id="findMessages" resultMap="messageEntityMap">
    SELECT id, conversation_id, role, content, model_name, token_count, created_at
    FROM message
    WHERE conversation_id = #{conversationId}
    ORDER BY created_at, id
</select>
```

网页点击历史会话时调用该查询，而不是 Redis。`created_at` 相同的极端情况下再按 UUID `id` 排序，使返回顺序稳定。完整历史可能超过 12 条，因此不能用第五周的短上下文缓存代替它。

调试时观察 Controller 接收到的 `conversationId` 是否与 SQL 参数一致，并直接检查 `message` 表是否有 USER/ASSISTANT 成对记录。

### 11.4 知识导入为何使用 checksum 去重

代码位置：`backend/business-service/src/main/java/com/petassistant/business/service/KnowledgeService.java` 的 `importDocument()`。

```java
AiKnowledgePreprocessResponse processed = knowledgeAiClient.preprocess(request);
KnowledgeDocumentProjection existing = mapper.findByChecksum(processed.checksum());

if (existing != null) {
    replaceChunksWhenProcessingChanged(existing, processed.chunks(), now);
    return new KnowledgeImportResponse(
            existing.id(), existing.title(), existing.checksum(),
            processed.chunks().size(), false
    );
}
```

FastAPI 先对清洗后的正文计算 SHA-256。相同正文再次导入时复用文档主键；若 embedding 模型或分块结果发生变化，则只重建分块。这样既避免重复文档，又允许第五周升级 BGE。

调试重复导入时观察响应的 `created`：`false` 表示正文已存在，不代表请求失败。
