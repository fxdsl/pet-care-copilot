# 第七周：用户认证、角色权限与数据归属

## 1. 本周目标与完成情况

第七周为后续宠物社区、知识投稿、统一搜索和推荐建立统一身份边界，并把第六周遗留的全局会话、全局宠物档案迁移为当前用户私有数据。

- [x] Spring Security 无状态过滤链，除认证和健康检查外，业务接口默认必须登录。
- [x] 注册和登录使用 MyBatis + MySQL，密码使用 BCrypt（强度 12）单向散列。
- [x] 访问令牌使用 HS256 JWT，默认 15 分钟；JWT 只保存用户 ID、用户名和角色。
- [x] 刷新令牌使用 256 位随机不透明令牌，Redis 只保存 SHA-256 摘要，默认 7 天。
- [x] Redisson 分布式锁保护刷新令牌旋转，旧令牌不能并发重放。
- [x] Redis Lua 原子计数实现 IP 频率限制和用户名失败冻结。
- [x] 用户资料使用 Redis Hash Cache-Aside，缓存故障时回源 MySQL。
- [x] 角色支持 `USER`、`VERIFIED_SELLER`、`MODERATOR`、`ADMIN`；知识管理仅 `ADMIN` 可用。
- [x] 会话、消息和宠物档案全部使用当前 JWT 用户 ID 做所有权校验。
- [x] 宠物档案增加网页编辑和删除功能，越权与不存在统一返回 404。
- [x] Flyway `V5` 已在本机 MySQL 8.0 成功执行，数据库版本从 4 升级为 5。
- [x] Java 25 项、Python 10 项测试通过；Vue TypeScript 检查和生产构建通过。

Spring Security 将认证主体保存在 `SecurityContextHolder`，并在过滤链结束时清理；项目由自定义 JWT Filter 在 Controller 之前建立主体。参考：[Spring Security Authentication Architecture](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/architecture.html)。Redisson 4.6.1 用于分布式锁，参考：[Redisson Getting Started](https://redisson.pro/docs/getting-started/)。

## 2. 完整调用链

### 2.1 注册和登录

```text
Vue 登录/注册表单
  → AuthController（公开接口 + Jakarta Validation）
  → LoginAttemptService（Redis Lua：IP 频率、失败次数）
  → AuthService
       ├─ UserMapper XML 查询/写入 app_user
       ├─ BCryptPasswordEncoder 校验或生成 password_hash
       ├─ JwtTokenService 签发 15 分钟访问令牌
       └─ RefreshTokenService 在 Redis 保存 7 天刷新令牌摘要
  → Vue 将令牌对和安全用户摘要存入 localStorage
```

### 2.2 已登录业务请求

```text
Vue apiRequest()
  → Authorization: Bearer <accessToken>
  → JwtAuthenticationFilter 验签、检查 issuer/exp、恢复 ROLE_*
  → SecurityFilterChain 判断是否登录以及是否为 ADMIN
  → Controller 从 Principal#getName() 获取 userId
  → Service / MyBatis 使用 userId 过滤会话或宠物档案
```

浏览器不能在请求 Body 中指定 `userId`。即使篡改会话 ID 或宠物档案 ID，SQL 的 `id + user_id` 条件也不会返回其他用户数据。

### 2.3 自动刷新

```text
业务请求收到 401
  → 前端合并同时发生的刷新请求
  → Redis 读取 auth:refresh:{tokenId}
  → Redisson 获取 auth:refresh:lock:{tokenId}
  → 常量时间比较 SHA-256 摘要
  → 删除旧 Key并创建新刷新令牌
  → 签发新 JWT
  → 原业务请求只重试一次
```

Redis 无法使用时，用户资料缓存和会话上下文可以回源 MySQL；注册、登录签发刷新令牌和刷新操作则返回 `503 AUTH_SESSION_UNAVAILABLE`，不能伪造一个无法撤销的登录会话。

## 4. 数据模型

### 4.1 `app_user`

| 字段 | 类型 | 约束/含义 |
|---|---|---|
| `id` | CHAR(36) | UUID 主键 |
| `username` | VARCHAR(64) | 唯一；接口限制 4～32 位字母、数字、下划线，统一小写 |
| `password_hash` | VARCHAR(100) | BCrypt 散列，禁止保存或返回明文 |
| `display_name` | VARCHAR(100) | 昵称 |
| `role` | VARCHAR(30) | USER / VERIFIED_SELLER / MODERATOR / ADMIN |
| `status` | VARCHAR(20) | ACTIVE / DISABLED / LOCKED |
| `avatar_url` | VARCHAR(1000) | 可空头像地址 |
| `bio` | VARCHAR(500) | 可空简介 |
| `region` | VARCHAR(100) | 可空地区 |
| `last_login_at` | TIMESTAMP(6) | 最近成功登录时间 |
| `created_at/updated_at` | TIMESTAMP(6) | 创建和更新时间 |

历史用户没有可验证密码，迁移时写入不可登录占位散列并将状态设为 `DISABLED`，避免自动分配默认密码。

### 4.2 数据归属

- `conversation.user_id` 在 V1 已存在；第七周新建会话强制写当前用户，列表和详情按 userId 查询。
- `pet_profile.user_id` 由 V5 新增并外键关联 `app_user`。
- 历史匿名会话和档案仍保留在 MySQL，`user_id IS NULL` 的记录不会被登录用户接口查询到。
- 不修改已经执行过的 V1～V4；所有新结构只通过 V5 增量迁移。

## 5. Redis Key 设计

| Key | 类型 | 示例值 | TTL | 写入/读取 | 故障行为 |
|---|---|---|---|---|---|
| `auth:refresh:{tokenId}` | String | `userId:sha256(secret)` | 7 天 | 登录/刷新写；刷新/退出读 | 503，不能绕过 |
| `auth:refresh:lock:{tokenId}` | Redisson Lock | 锁对象 | 最长 5 秒租约 | 刷新 | 503 或认证失败 |
| `auth:login:fail:{username}` | String 计数 | `3` | 15 分钟 | 登录失败写，登录前读 | 记录 warning 后继续真实密码认证 |
| `auth:rate:login:{ip}` | String 计数 | `8` | 1 分钟 | 登录入口 | Redis 故障不跳过密码认证 |
| `auth:rate:register:{ip}` | String 计数 | `2` | 1 分钟 | 注册入口 | Redis 故障仍校验字段和唯一索引 |
| `user:session:{userId}` | Hash | username/role/status 等 | 15 分钟 | 用户资料接口 | 回源 MySQL |
| `conversation:context:{id}` | JSON String | 最近 12 条消息 | 30 分钟 | Agent 上下文 | 先验证所有权，再回源 MySQL |

刷新令牌原文为 `tokenId.secret`，Redis 从不保存 `secret`；比较摘要使用 `MessageDigest.isEqual`，降低简单字符串比较造成的时序差异。

## 6. 核心代码讲解

### 6.1 SecurityFilterChain 默认拒绝匿名业务请求

代码位置：`config/SecurityConfig.java` 的 `securityFilterChain()`。

```java
http
    .csrf(csrf -> csrf.disable())
    .cors(Customizer.withDefaults())
    .sessionManagement(session ->
        session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .authorizeHttpRequests(authorize -> authorize
        .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()
        .requestMatchers("/api/v1/auth/**", "/api/v1/system/health",
                         "/actuator/health", "/error").permitAll()
        .requestMatchers("/api/v1/knowledge/**").hasRole("ADMIN")
        .anyRequest().authenticated())
    .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
```

执行过程：认证和健康检查公开；知识管理要求 `ROLE_ADMIN`；其他新旧接口默认要求登录。项目不启用表单登录和 HTTP Basic，也不使用服务器 HttpSession。

调试时观察：断点放在 `JwtAuthenticationFilter`，查看 Authorization 头、`AuthenticatedUser.userId` 和 `SecurityContextHolder.getContext().getAuthentication()`；不要打印完整令牌。

### 6.2 注册时密码只保存 BCrypt

代码位置：`service/AuthService.java` 的 `register()`。

```java
String username = normalizeUsername(request.username());
if (userMapper.findByUsername(username) != null) {
    throw new UsernameAlreadyExistsException();
}
UserEntity user = new UserEntity(
    UUID.randomUUID().toString(), username,
    passwordEncoder.encode(request.password()),
    resolvedDisplayName, "USER", "ACTIVE",
    null, null, null, now, now, now
);
userMapper.insert(user);
return issueTokenPair(user);
```

执行过程：先统一用户名大小写，再检查业务冲突；MySQL 唯一索引仍处理并发注册竞态。注册角色固定为 USER，浏览器不能传 role。Redis 无法保存刷新令牌时抛异常，数据库事务回滚。

调试时观察：只确认 `password_hash` 以 BCrypt 格式保存，不要在日志或断点截图传播 request.password。

### 6.3 刷新令牌在分布式锁内旋转

代码位置：`service/RefreshTokenService.java` 的 `rotate()`。

```java
RLock lock = redissonProvider.getObject()
    .getLock("auth:refresh:lock:" + parts.tokenId());
boolean acquired = lock.tryLock(1, 5, TimeUnit.SECONDS);
if (!acquired) throw new AuthenticationFailedException();
String stored = redisTemplate.opsForValue().get(key(parts.tokenId()));
String userId = validateStored(stored, parts.secret());
redisTemplate.delete(key(parts.tokenId()));
return new RotatedToken(userId, issue(userId));
```

执行过程：两个实例同时收到同一令牌时，只有一个获得锁；成功者删除旧 Key 并创建新令牌，后续请求读取不到旧 Key。锁只是跨实例互斥，令牌有效性仍由随机 secret 摘要决定。

调试时观察：Redis Key 是否设置 TTL、旧 Key 是否删除、新 tokenId 是否不同；不要查看或复制完整 secret。

### 6.4 会话缓存命中前仍验证所有权

代码位置：`service/ConversationService.java` 的 `getRecentMessagesForContext()`。

```java
requireConversation(userId, conversationId);
var cached = contextCacheService.get(conversationId);
if (cached.isPresent()) {
    return tail(cached.get(), safeLimit);
}
List<ConversationContextMessage> context = mapper
    .findRecentMessages(conversationId, safeLimit).stream()
    .map(message -> new ConversationContextMessage(
        message.role(), message.content()))
    .toList();
contextCacheService.put(conversationId, context);
```

如果先读 Redis 再验证数据库归属，攻击者只要拿到 UUID 就可能读到他人上下文。因此即使缓存命中也先执行轻量所有权 SQL；Redis 省去的是消息正文查询，不省略安全检查。

调试时观察：`findByIdAndUser(id,userId)` 返回值、是否在归属失败时调用了 `contextCacheService.get`；对应单测明确断言“先拒绝、后不读缓存”。

### 6.5 MyBatis 使用复合条件隔离宠物档案

代码位置：`resources/mapper/PetProfileMapper.xml`。

```xml
<select id="findByIdAndUser" resultMap="petProfileEntityMap">
    SELECT id, user_id, name, pet_type, breed, age_months,
           weight_kg, notes, created_at, updated_at
    FROM pet_profile
    WHERE id = #{id} AND user_id = #{userId}
</select>

<update id="update">
    UPDATE pet_profile
    SET name = #{name}, pet_type = #{petType}, breed = #{breed},
        age_months = #{ageMonths}, weight_kg = #{weightKg},
        notes = #{notes}, updated_at = #{updatedAt}
    WHERE id = #{id} AND user_id = #{userId}
</update>
```

Service 创建实体时 userId 取自 JWT Principal；Mapper 所有读写都绑定 userId。越权和不存在统一返回 404，不暴露某个档案是否属于其他用户。

调试时观察：IDEA MyBatisX 从 Mapper 跳到 XML，确认 SQL 参数中的 userId 与 JWT subject 一致。

### 6.6 前端 401 只自动刷新一次

代码位置：`frontend/src/api/http.ts` 的 `apiRequest()`。

```ts
if (
  response.status === 401 &&
  allowRefresh &&
  !path.startsWith('/api/v1/auth/') &&
  (await refreshAccessToken())
) {
  return apiRequest<T>(path, init, false)
}
```

多个并发 401 共用 `refreshInFlight`，避免同时旋转同一个刷新令牌。重试时 `allowRefresh=false`，防止 Redis、JWT 或权限错误造成无限循环。注册、登录自身失败不会触发刷新。

调试时观察：Network 中原请求 401、刷新 200、原请求重试 200；若刷新 401，本地会话被清除并回到登录页。

## 7. API 公共规则

- Base URL：`http://localhost:8080`。
- 除认证和健康接口外，请求头必须包含 `Authorization: Bearer <accessToken>`。
- 外部 JSON 使用驼峰命名；时间为 ISO-8601 字符串。
- 通用错误结构：`code:string`、`message:string`、`timestamp:string`。

下文所有接口如果未单独说明，Path 参数、Query 参数或 Body 中没有的类别均为“无”。

## 15. 常见问题

### 页面只显示登录框

这是第七周正常行为。注册或登录需要 MySQL 和 Redis 同时启动；问答还需要 FastAPI。

### 注册/登录返回 `AUTH_SESSION_UNAVAILABLE`

MySQL 账号可能已经写入前失败并回滚，但刷新令牌无法写 Redis。确认 6379 端口、`REDIS_HOST/PORT/PASSWORD` 后重试。

### 普通用户看不到知识库按钮

知识导入属于 ADMIN 权限。使用 bootstrap 配置首次创建管理员；不要直接让所有注册用户上传可信知识，社区知识投稿会在第十一周经过授权和审核流程接入。

### 旧会话或档案消失

第六周及以前创建的数据没有用户归属，仍保留在数据库但不会暴露给任何登录用户。新账号第一次提问会建立自己的会话。若确需认领历史数据，应单独编写一次性、可审计的数据迁移，不能恢复全局查询。

### 访问令牌到期后反复回登录页

检查 Network 中刷新接口。刷新令牌可能已退出、过期、被另一个标签页旋转或 Redis 数据被清理；前端只重试一次，失败后要求重新登录。
