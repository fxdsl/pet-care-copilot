# 开发文档规范：第六周起强制执行

## 1. 为什么制定这份规范

开发文档不能只记录“做了什么”，还必须帮助读者回答以下问题：

1. 用户在网页点击按钮后，代码依次进入哪些文件和方法？
2. 每一层收到什么数据、返回什么数据？
3. 核心判断、事务、缓存和降级为什么这样设计？
4. 出现问题时应该在哪一层打断点、看哪个字段和日志？
5. 本周替换了哪些旧实现，哪些历史迁移文件必须保留？

因此，从第六周开始，每周文档必须包含“核心代码讲解”，不能只列目录、接口和启动命令。

## 2. 每周文档固定结构

每一周至少包含以下章节：

1. **目标与完成情况**：使用可验收的清单，不写模糊表述。
2. **完整调用链**：从 Vue 到 Spring Boot、FastAPI、MySQL/Redis，再回到页面。
3. **目录与职责**：说明新增和变更文件，尤其是 Java 分层位置。
4. **数据模型或状态模型**：数据库字段、Redis Key、前端状态或 Agent State。
5. **核心代码讲解**：本规范第 3 节的重点内容。
6. **API 契约**：每一个接口都列出 Path、Query、Body、响应、错误码及全部字段含义。
7. **配置说明**：默认值、环境变量、敏感信息和费用边界。
8. **启动与调试**：IDEA Java、IDEA Python、VS Code 的具体方法。
9. **自动化测试和手工验收**：命令、覆盖点、实际结果。
10. **常见问题**：症状、定位方法、根因和解决步骤。
11. **旧代码迁移说明**：删除什么、保留什么、为何不保留兼容分支。
12. **下一周衔接**：只写尚未完成的内容。

## 3. 核心代码讲解的写法

### 3.1 每段讲解必须包含五项

每个核心代码片段都必须同时写明：

- **代码位置**：精确到项目相对路径、类和方法。
- **职责**：这段代码负责什么、不负责什么。
- **关键代码**：截取 8～35 行最能说明问题的代码，省略无关样板。
- **执行过程**：按顺序解释数据和控制流，而不是逐字翻译语法。
- **调试观察点**：建议断点、关键变量、日志或数据库记录。

示例格式：

```markdown
### X.X Java 问答事务

代码位置：`backend/.../service/ChatService.java` 的 `answer()`。

```java
// 只保留体现核心逻辑的代码
```

执行过程：

1. ……
2. ……

调试时观察：`conversationId`、`history`、`aiResponse.routingReason()`。
```

### 3.2 必须覆盖的核心代码类型

第六周及以后，每周根据实际功能至少选择 5 个核心点：

- Vue 入口事件和请求状态管理。
- Java Controller 的接口边界。
- Java Service 的业务编排或事务边界。
- MyBatis Mapper 接口与 XML 中的关键 SQL。
- Java 到 FastAPI 的内部 DTO 和 HTTP Client。
- FastAPI 路由、服务算法或 LangGraph 节点。
- Redis Key、Cache-Aside、锁或幂等逻辑。
- 数据库迁移与关键索引。
- 异常降级、超时、循环终止和资源上限。
- 对应自动化测试为什么能证明功能正确。

### 3.3 代码片段的约束

- 代码必须来自当前工作区的真实实现，不能写伪代码冒充已完成代码。
- 片段只保留核心上下文，不把整个文件复制进文档。
- 代码升级后同步更新文档；若讲的是历史版本，必须标注“历史实现，现已被某实现替代”。
- 已删除的旧接口和旧类只能用于解释迁移原因，不能再作为当前使用方法。
- 讲解重点是业务含义、边界和设计取舍，不是逐行翻译 Java/Python/TypeScript 语法。
- 所有敏感值必须使用占位符，禁止把 API Key、密码或真实用户内容写入文档。

## 4. 第六周 LangGraph 文档额外要求

第六周接入 LangGraph 时，文档还必须包含：

- Agent State 的字段定义和每个字段由谁写入。
- 每个节点的输入、输出、副作用和失败方式。
- 条件边的判断代码及可能进入的下一节点。
- ReAct 工具调用循环的最大步数、终止条件和异常中断条件。
- 工具白名单与参数校验，说明为什么不能让模型任意调用接口。
- RAG 节点、通用模型节点和安全节点的关系。
- 一次完整请求的状态变化示例。
- 单元测试如何覆盖正常路径、工具异常和循环上限。

### 4.1 每个接口的强制参数表

文档中只要出现一个接口地址，就必须在本周的“接口参数字典”中找到对应说明。每个接口至少包含：

- HTTP 方法和完整路径。
- 调用方与接收方，例如“Vue → Spring Boot”或“Spring Boot → FastAPI”。
- Path 参数：名称、类型、必填性和含义；没有时明确写“无”。
- Query 参数：名称、类型、必填性、默认值、允许范围；没有时明确写“无”。
- Body 参数：每个字段的 JSON 名称、类型、必填性、默认值、长度/枚举约束和含义。
- 嵌套对象与数组：单独列出子字段，不能只写“对象”或“候选列表”。
- 成功响应：状态码以及每个响应字段的类型、是否可能为空和含义。
- 错误响应：可能的 HTTP 状态、业务 `code` 和触发条件。
- 每条业务链至少提供一组与真实 DTO 一致的请求/响应示例；简单 GET 可以只给参数表和响应字段表。

字段命名必须与实际序列化结果一致：浏览器和 Java 外部接口使用驼峰，Java 调用 FastAPI 的内部接口使用蛇形。不能把 Java record 属性名、数据库列名和 JSON 字段名混在同一张表中。

## 5. 文档验收清单

每周结束前逐项确认：

- [ ] 能从页面按钮一路找到最终数据库、Redis 或模型调用。
- [ ] 至少 5 个核心代码片段有路径、解释和调试观察点。
- [ ] API 请求与响应示例和真实 DTO 一致。
- [ ] 文档出现的每个接口都有完整 Path/Query/Body/响应参数表。
- [ ] 数据库字段与最新 Flyway 迁移一致。
- [ ] Redis 或 Agent 状态给出了具体结构示例。
- [ ] 启动命令在当前 Windows 环境实际执行过。
- [ ] 测试数量和结果来自真实运行，不凭空填写。
- [ ] 已删除代码没有继续出现在“当前接口”中。
- [ ] README 的周进度和链接已经同步。

第一到第五周已经补充“核心代码讲解”章节；这些补充以当前最终代码为准，并对被后续周替代的历史实现进行了标注。

## 6. 规划文档与实施文档的边界

`后续开发路线.md` 只用于记录尚未实现的业务安排、技术选择、周次和验收目标，不得把计划写成“已经完成”。规划阶段可以描述候选数据表、Redis Key 和中间件，但不提前固定 HTTP 接口地址，以免规划接口与最终 DTO、权限和代码不一致。

一旦某项功能进入实际开发，对应的“第几周”实施文档必须：

- 使用当前工作区的真实类、方法、SQL、Flyway 迁移和自动化测试结果。
- 给本周实际存在的每一个 HTTP 接口补齐完整参数字典，不得仅引用路线文档。
- 明确规划与实际实现的差异、删掉的旧实现和最终采用的 Redis Key/TTL。
- 将 README 中对应周次标记为完成，并链接本周实施文档。

## 7. 数据库文档同步规则

`docs/数据库文档.md` 是跨周维护的当前数据库总览，周开发文档负责解释“本周为什么变化”，两者不能互相替代。

凡是新增或修改 Flyway 迁移、Entity、Mapper SQL、Redis 数据结构、MinIO 元数据或 Outbox 事件结构，同一次开发必须同步：

1. 更新数据库文档顶部的 Flyway 版本和同步日期。
2. 更新业务表总览、ER 图、完整字段、默认值、索引、外键和删除策略。
3. 更新状态枚举、最终事实来源、缓存回源和重建策略。
4. 更新 Flyway 迁移历史；已经执行的旧迁移只能记录，不能修改。
5. 在对应周文档中讲解本周迁移核心 SQL，并链接数据库文档。
6. 运行迁移测试或使用 `information_schema` 只读核对，不根据记忆手写不确定字段。

代码审查时，如果存在新的 `V*__*.sql` 而数据库文档没有同步，该周任务视为未完成。
