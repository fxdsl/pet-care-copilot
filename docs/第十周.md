# 第十周：消息中心、他人主页与 Agent 流式回答

> 完成日期：2026-08-24  
> 数据库版本：Flyway `V8`  
> 技术范围：Spring Boot、MyBatis XML、MySQL、Redis Hash/Stream/Pub/Sub、WebSocket、SSE、FastAPI、Vue 3、Pinia  
> 安全边界：所有业务接口要求 Bearer JWT；公开主页中的“公开”是相对社区用户公开，不代表匿名访问

## 1. 本周完成结果

本周把社区互动、消息和问答串成了完整用户链路：

- 社区任意帖子、评论、推荐作者和关系列表中的头像/昵称均可进入他人主页。
- 他人主页展示公开资料、公开宠物摘要、发布、粉丝和关注；不返回密码、安全版本、最近登录时间和宠物备注。
- 个人页补齐“我的点赞、我的收藏、我的关注、我的粉丝”分页内容。
- 点赞、评论、关注和审核结果形成可查询的站内通知，导航显示未读角标。
- 消息中心提供通知分类和私信双栏；移动端使用会话列表/内容区切换。
- 私信正文和已读状态保存到 MySQL；`clientMessageId` 保证断线重试不重复发送。
- WebSocket 首帧认证、心跳、在线状态、跨实例 Pub/Sub 推送和 Redis 故障单机降级已实现。
- 问答改为 SSE：展示准备、检索、模型调用、答案片段、心跳、完成、失败、重连和取消状态。
- 相同 `requestId` 的 SSE 重连不会再次调用 Agent，也不会重复写入 USER/ASSISTANT 消息。
- 新增 Flyway V8 三张消息表，数据库文档同步到 21 张业务表。

消息中心只承接社区互动、审核、私信与系统通知，不预留尚不存在的业务通知。消息表通过 `COMMENT/LIKE/FOLLOW/MODERATION/SYSTEM` 承接当前事件，新增通知类型时仍须使用连续迁移和兼容的枚举扩展。

## 2. 总体调用链

```text
社区互动事务
  ├─ 写点赞/评论/关注事实
  └─ 写 user_notification（dedupe_key 唯一）
       └─ 事务提交后
            ├─ 删除 message:unread:{userId}
            ├─ XADD message:event:stream（仅 ID 与状态）
            └─ PUBLISH message:realtime:channel
                  └─ 当前实例 WebSocket → 消息中心刷新

发送私信
  → senderId + clientMessageId 幂等检查
  → 查找/创建唯一 direct_conversation
  → 写 direct_message + 更新会话时间
  → 提交后删接收人未读缓存并推送消息 ID

浏览器 POST /api/v1/chat/stream
  → Java ChatStreamingService（连接上限、requestId、Last-Event-ID）
  → Java ChatService（会话/档案/知识候选）
  → FastAPI POST /api/v1/agent/answer/stream
  → 脱敏阶段 + token 片段
  → Java 成功保存问答消息
  → Java result + done
```

这里刻意把“最终事实”和“加速数据”分开：通知、私信和完成后的问答消息以 MySQL 为准；Redis/Pub/Sub/WebSocket/SSE 故障不能让离线消息消失。

## 3. 数据库 V8

迁移文件：`backend/business-service/src/main/resources/db/migration/V8__add_messaging_notifications_and_realtime.sql`。

### 3.1 三张新表

| 表 | 最终事实 | 关键约束 |
|---|---|---|
| `user_notification` | 站内通知、接收人、触发人、目标和已读时间 | `UNIQUE(recipient_id, dedupe_key)` |
| `direct_conversation` | 两位用户之间的唯一私信会话 | `UNIQUE(participant_low_id, participant_high_id)`，并要求 low < high |
| `direct_message` | 私信正文、发送/接收人、已读时间 | `UNIQUE(sender_id, client_message_id)` |

`dedupe_key` 由业务事件稳定生成。例如同一用户对同一帖子的点赞可使用 `like:{postId}:{actorId}`。消息重复投递或用户取消后再次点赞时，唯一约束会让同一业务事实只产生一次通知，不会重复增加未读数。

私信参与者不使用“发起人/接收人”确定会话，而是先按 UUID 字典序排序：

```java
String low = userId.compareTo(recipientId) < 0 ? userId : recipientId;
String high = userId.compareTo(recipientId) < 0 ? recipientId : userId;
DirectConversationEntity conversation = mapper.findConversationByPair(low, high);
```

这样 A 给 B 发私信与 B 给 A 回复始终落在同一条 `direct_conversation`。

完整字段、索引、外键和删除策略见[数据库文档](数据库文档.md)。

### 4.1 通知事务与幂等

`MessageService.createNotification` 在原业务事务中先写 MySQL。数据库唯一索引捕获重复通知；只有事务成功提交后才清未读缓存和推送：

```java
try {
    mapper.insertNotification(entity);
} catch (DuplicateKeyException duplicate) {
    return;
}
afterCommit(() -> {
    evictUnread(recipientId);
    realtimeEventService.publish(recipientId, "NOTIFICATION_CREATED", Map.of(
            "notificationId", entity.id(), "notificationType", type
    ));
});
```

如果事务回滚，浏览器不会收到一条数据库中不存在的通知。点赞/关注等调用点统一位于 `CommunitySocialService`，没有让 Controller 拼通知。

### 4.2 未读数 Cache-Aside

`GET /api/v1/messages/unread` 先读 `message:unread:{userId}`。Hash 为空或 Redis 不可用时，分别聚合 `user_notification.read_at IS NULL` 和 `direct_message.read_at IS NULL`，再重建 Hash。写通知、写私信和标记已读后删除整 Key，下一次读取重新聚合。

这比对 Hash 直接 `HINCRBY` 更容易保证最终正确：应用崩溃、重复事件或缓存被清空都能从 MySQL 恢复。

### 4.3 私信幂等与所有权

前端每次发送生成 UUID `clientMessageId`，失败重试必须复用该值。服务先查已有记录，插入并发冲突时再次查询并返回原消息：

```java
DirectMessageView existing = mapper.findDirectMessageByClientId(userId, request.clientMessageId());
if (existing != null) return toDirectMessage(existing);
try {
    mapper.insertDirectMessage(entity);
} catch (DuplicateKeyException duplicate) {
    return toDirectMessage(mapper.findDirectMessageByClientId(userId, request.clientMessageId()));
}
```

读取私信前通过 MyBatis SQL 同时校验 `participant_low_id = currentUser` 或 `participant_high_id = currentUser`。客户端不能通过修改 URL 读取他人的私信。

### 4.4 公开主页的数据边界

`CommunityProfileService` 单独组装 `PublicUserProfileResponse`，没有复用“我的资料” DTO。公开宠物摘要只有 `id/name/petType/breed/ageMonths`，不包含健康备注；他人的宠物也不会被带入当前用户 Agent 上下文。

帖子、评论、推荐用户和粉丝/关注卡片均链接 `/app/users/{userId}`。通知跳到社区时使用 `?post={postId}`，`CommunityView` 会直接加载目标详情，即使帖子不在当前首屏。

### 4.5 WebSocket 安全与实时推送

连接地址为 `ws://localhost:8080/ws/realtime`。JWT 不放 URL，防止进入代理和访问日志。建立连接后服务端先发：

```json
{"type":"AUTH_REQUIRED"}
```

浏览器第一帧必须发送：

```json
{"type":"AUTH","token":"<access-token>"}
```

认证通过返回 `AUTHENTICATED`。浏览器每 25 秒发送 `{"type":"PING"}`，服务端返回 `PONG`，并把 `message:presence:{userId}` 续期到 75 秒。同一账号最多 3 个实时连接。

推送信封示例：

```json
{
  "eventId": "8c7a...",
  "recipientId": "user-b",
  "type": "DIRECT_MESSAGE_CREATED",
  "payload": {"messageId":"m-1","conversationId":"c-1","senderId":"user-a"},
  "createdAt": "2026-08-24T10:30:00Z"
}
```

Redis Stream 和推送载荷只保存 ID 与状态，不保存私信正文。前端收到后重新读取受鉴权 HTTP 接口。Pub/Sub 不保证离线投递，因此离线用户登录后仍从 MySQL 查询。

### 4.6 Java SSE 会话管理

`ChatStreamingService` 使用固定 8 线程池、50 条活动流上限、每请求 2,000 条有界事件、135 秒连接超时和完成后 10 分钟缓冲。断线只移除当前 `SseEmitter`，后台任务继续；客户端用同一 `requestId` 和 `Last-Event-ID` 重连并重放缺失事件。

FastAPI 的 `result/done` 不直接透传。Java 必须先成功保存 USER/ASSISTANT 消息，再发送 Java `ChatResponse` 和 `done`，防止页面显示“完成”但刷新后没有历史消息。

## 5. Redis Key 完整说明

| Key | 类型 | 示例内容 | TTL/上限 | 写入/失效/回源 |
|---|---|---|---|---|
| `message:unread:{userId}` | Hash | `COMMENT=2, LIKE=1, DIRECT_MESSAGE=3, TOTAL=6` | 无固定 TTL | 通知/私信/已读提交后删除；从两张 MySQL 事实表重建 |
| `message:presence:{userId}` | String | `ONLINE` | 75 秒 | WebSocket 认证和 PING 续期；最后连接断开删除；不回源 |
| `message:event:stream` | Stream | `eventId/recipientId/type/payload/createdAt` | 最多 10,000 条 | 事务提交后 XADD；仅用于有界事件记录，完整内容回源 MySQL |
| `message:realtime:channel` | Pub/Sub | 实时信封 JSON | 不持久化 | 跨 Java 实例在线广播；不承担离线可靠性 |

Agent SSE 事件缓冲目前属于单 JVM 的短期连接恢复，不冒充 Redis 持久化。服务重启后，已完成答案从 MySQL 会话恢复；正在运行的流应显示失败并由用户以新 `requestId` 重试。未来做多实例跨节点恢复时再使用独立 Agent Stream，不能与站内消息 Stream 混用。

## 6. HTTP 接口总览

除 FastAPI 内部接口外，以下接口均使用：

```http
Authorization: Bearer <access-token>
Content-Type: application/json
```

分页统一从 0 开始。通知最大 `size=100`，私信会话最大 50，私信消息最大 100，用户关系最大 50。

### 6.1 `GET /api/v1/community/users/{userId}/profile`

- Path：`userId`，目标用户 UUID。
- Query：无。
- Body：无。
- 200：

```json
{
  "id":"user-b","username":"xiaoming","displayName":"小明","avatarUrl":null,
  "bio":"金毛家长","region":"安徽合肥","joinedAt":"2026-08-01T01:00:00Z",
```

### 6.2 `GET /api/v1/community/users/{userId}/followers`

- Path：`userId`。
- Query：`page` 默认 0；`size` 默认 20，后端限制 1～50。
- Body：无。
- 200：`{"items":[PublicUserSummary],"page":0,"size":20,"total":12}`。

#### 主页复用的帖子接口

他人主页和通知跳转还复用第九周帖子接口，本周实际传参如下：

- `GET /api/v1/community/posts?feed=LATEST&authorId={userId}&page=0&size=30`：Path 无；Query 中 `authorId` 为主页用户，`feed` 默认 `LATEST`，`topicId` 可选，`page` 从 0 开始，`size` 后端限制 1～50；附近流才需要 `latitude/longitude/radiusKm`。Body 无。200 返回 `CommunityPostPageResponse(items/page/size/total)`；400 表示 feed/坐标参数非法，401 未登录，503 数据库不可用。

### 6.10 `GET /api/v1/messages/conversations`

- Query：`page` 默认 0；`size` 默认 30，限制 1～50。
- 200：`items/page/size/total`。每项包含 `id/otherUserId/otherUsername/otherDisplayName/otherAvatarUrl/lastMessageContent/lastMessageMine/lastMessageAt/unreadCount/createdAt/updatedAt`。
- 错误：401、503。

### 6.11 `GET /api/v1/messages/conversations/{conversationId}`

- Path：`conversationId`。
- Query：`page` 默认 0；`size` 默认 100，限制 1～100。
- Body：无。
- 200：`items/page/size/total`；读取成功会把当前用户收到的该会话消息标记已读。每条消息包含 `id/conversationId/senderId/senderUsername/senderDisplayName/senderAvatarUrl/recipientId/clientMessageId/content/read/createdAt`。
- 错误：400（会话不存在或当前用户不是参与者）；401；503。

### 6.12 `POST /api/v1/messages/direct`

- Body：

```json
{"recipientId":"user-b","clientMessageId":"7df5d89e-...","content":"你好，想交流一下幼猫喂养。"}
```

- 校验：`recipientId/clientMessageId/content` 必填；前两项最多 36 字符；正文最多 2,000 字符；不能给自己发送。
- 201：返回持久化 `DirectMessageResponse`。相同发送人和 `clientMessageId` 重试时返回原消息，不新增记录。
- 错误：400 `INVALID_REQUEST`；401；503。

### 6.13 `POST /api/v1/chat/stream`

- Header：`Last-Event-ID` 可选，必须为非负整数；首次不传，断线重连传最后成功处理的事件 ID。
- Body：

```json
{
  "requestId":"f3cd6b7f-...",
  "question":"幼猫一天应该喂几次？",
  "conversationId":null,
  "petProfileId":null,
  "petType":"CAT",
  "category":"FEEDING"
}
```

- 校验：`requestId/question` 必填；问题最多 2,000 字符；各 ID 最多 36；类型最多 30；分类最多 50。
- 200：`text/event-stream`，事件见第 7 节。
- 错误：400（参数、Last-Event-ID 或 requestId 冲突）；401；502 `AI_SERVICE_UNAVAILABLE`；500 `INTERNAL_ERROR`。活动流超过 50 时当前返回 500 和可理解提示，后续可单独映射为 429。

### 6.14 `DELETE /api/v1/chat/streams/{requestId}`

- Path：`requestId`。
- Query/Body：无。
- 204：停止成功；流中先发送 `cancelled`。
- 错误：400（请求不存在或不属于当前用户）；401。

### 6.15 FastAPI 内部 `POST /api/v1/agent/answer/stream`

该接口由 Java 调用，浏览器不得绕过 Java 直接访问。Body 与原 `AgentRequest` 一致，包括 `question/candidateChunks/conversationHistory/petProfile` 等 Agent 上下文；响应为 SSE。并发 Semaphore 为 16，单次最大等待 120 秒，每 5 秒心跳。超时事件为 `error`，`code=AGENT_TIMEOUT`。

## 7. SSE 事件契约

每帧包含递增 `id`、`event` 和 JSON `data`：

```text
id: 12
event: token
data: {"text":"幼猫通常需要少量多餐"}
```

| event | data 关键字段 | 前端行为 |
|---|---|---|
| `stage` | `stage/message/action/status` | 显示准备、检索、模型调用等脱敏状态 |
| `heartbeat` | `stage/message` | 保持连接并更新“仍在处理”提示 |
| `token` | `text` | 追加到当前助手气泡并显示光标 |
| `result` | 完整 `ChatResponse` | 用最终答案、来源、模型和会话 ID 校正界面 |
| `done` | `conversationId/terminationReason` | 停止光标并完成本次流 |
| `error` | `code/message` | 显示失败和重试按钮 |
| `cancelled` | `message` | 显示已停止 |

事件只包含公开阶段和答案片段，不返回隐藏思维过程、系统提示词、API Key、原始工具观察或完整宠物敏感档案。

## 8. 前端页面与交互

### 8.1 消息中心

- 路由：`/app/messages`。
- 桌面端：左侧通知/私信模式，中间会话或通知列表，右侧内容。
- 移动端：先显示会话列表，选择后进入单会话内容区。
- 导航角标来自 Pinia `message` Store；收到 WebSocket 事件后重新读取未读和当前列表。
- 通知点击：帖子目标进入 `/app/community?post={id}`；用户目标进入 `/app/users/{id}`。

### 8.2 他人主页

- 路由：`/app/users/:userId`。
- 展示头图、头像、昵称、简介、地区、加入时间、宠物摘要、公开帖子、粉丝和关注。
- 非本人显示“关注/取消关注”和“发私信”；发私信跳转 `/app/messages?user={userId}`。
- 本人访问该路由时仍按公开边界展示，资料编辑继续使用 `/app/account`。

### 8.3 问答页

- 发送时生成一次 UUID `requestId`，自动重连最多 3 次且不改变 requestId。
- 网络断开时带 `Last-Event-ID`，界面显示“正在恢复”。
- “停止生成”调用 DELETE 接口并中止浏览器读取；失败可使用新 requestId 重试。

## 9. 错误响应统一结构

非 SSE HTTP 错误沿用：

```json
{"code":"INVALID_REQUEST","message":"通知类型筛选无效","timestamp":"2026-08-24T02:00:00Z"}
```

401/403 由 Spring Security 返回；数据库错误不会暴露 SQL、连接串或密码。WebSocket 认证失败关闭连接，原因是“访问令牌无效”；首帧不是 AUTH 时关闭原因是“首帧必须完成认证”。

## 13. 个人主页左侧导航溢出修复

粉丝入口位于个人主页左侧菜单底部。窗口高度不足时，旧样式对整个 `.personal-side-nav` 使用 `overflow: hidden`，超过卡片高度的“我的粉丝”和“编辑个人资料”会被直接裁掉。

修复后左侧卡片使用纵向 Flex 布局：标题区和资料按钮不参与滚动，中间 `nav` 获得剩余高度并独立滚动。`min-height: 0` 允许导航作为 Flex 子项正确收缩，`overscroll-behavior: contain` 防止滚轮到达边界后带动中间内容栏。

```css
.personal-side-nav {
  display: flex;
  overflow: hidden;
  height: 100%;
  min-height: 0;
  flex-direction: column;
}

.personal-side-nav nav {
  overflow-y: auto;
  min-height: 0;
  overscroll-behavior: contain;
  scrollbar-gutter: stable;
  scrollbar-width: thin;
}

.personal-settings-link {
  flex: 0 0 auto;
}
```

Chromium/Safari 使用 `::-webkit-scrollbar` 定制 7px 滚动条，Firefox 使用 `scrollbar-width` 和 `scrollbar-color`。小于 1100px 时个人左栏仍按原响应式规则隐藏，因此不会在移动端额外出现窄滚动区。本次修改没有增加接口或改变粉丝分页参数。

## 14. 宠物档案功能区独立滚动

宠物档案页原来复用普通 `.content-page`，页面没有自己的高度和溢出边界，因此档案数量增加或窗口高度缩小时，滚轮会移动整个浏览器文档，顶部导航、标题和“新建档案”按钮也会一起离开视口。

修复分为两层：

1. `UserLayout.vue` 根据 `route.name === 'profiles'` 添加 `profiles-route`，把应用外壳固定为 `100dvh` 的两行 Grid；第一行是顶部导航，第二行是页面容器。
2. `ProfilesView.vue` 使用 `profiles-page` 把标题和功能区分成两行，只有 `profiles-scroll-region` 设置 `overflow-y: auto`。

```vue
<section class="profiles-page">
  <header class="page-heading">...</header>
  <div class="profiles-scroll-region" aria-label="宠物档案功能区">
    <PageState v-if="loading" ... />
    <div v-else class="profile-gallery">...</div>
  </div>
</section>
```

```css
.profiles-page {
  display: grid;
  overflow: hidden;
  height: 100%;
  min-height: 0;
  grid-template-rows: auto minmax(0, 1fr);
}

.profiles-scroll-region {
  overflow-y: auto;
  min-height: 0;
  overscroll-behavior: contain;
  scrollbar-gutter: stable;
}
```

加载、错误、空状态和档案卡片都位于同一个功能区，状态切换不会改变滚动边界；新建/编辑档案的 Element Plus Dialog 继续 Teleport 到页面外层并使用弹窗自身滚动。本次修改没有改变宠物档案接口或请求参数，Vue TypeScript 检查和生产构建通过。

## 15. 第十一周删除代码归档：直接导入知识库

> 本节只保存第十周结束时仍在使用、但已被第十一周审核工作流替换的核心代码，不能作为当前接口说明。当前契约请看[第十一周开发文档](第十一周.md)。

第十周的管理端可以在一次 HTTP 请求内完成“接收正文、调用 FastAPI、保存 READY 文档”。旧 Controller 的核心形式如下：

```java
/** 旧实现：管理员提交后直接导入，没有独立投稿和人工审核状态。 */
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public KnowledgeImportResponse importDocument(
        @Valid @RequestBody KnowledgeImportRequest request
) {
    return knowledgeService.importDocument(request);
}
```

旧 Service 会在当前请求线程中直接预处理并写入知识文档：

```java
/** 旧实现归档：预处理成功后立即把文档和分块作为 READY 数据保存。 */
@Transactional
public KnowledgeImportResponse importDocument(KnowledgeImportRequest request) {
    KnowledgePreprocessResponse processed = knowledgeAiClient.preprocess(request);
    String documentId = UUID.randomUUID().toString();
    knowledgeMapper.insertDocument(documentId, request, processed.checksum(), "READY");
    knowledgeMapper.insertChunks(documentId, processed.chunks());
    return new KnowledgeImportResponse(documentId, "READY", processed.chunks().size());
}
```

前端旧调用同样只有一个直接导入函数：

```ts
/** 旧实现归档：该地址已删除，不能继续调用。 */
export function importKnowledge(payload: KnowledgeImportPayload) {
  return apiRequest<KnowledgeImportResult>('/api/v1/knowledge/documents', {
    method: 'POST',
    body: JSON.stringify(payload),
  })
}
```

这套代码在第十一周整体删除，包括 `KnowledgeImportRequest`、`KnowledgeImportResponse`、旧 `KnowledgeDocumentEntity`、Mapper 的 `insertDocument`、Service 的 `importDocument` 和前端 `importKnowledge`。原因不是简单改名，而是它缺少授权证明、版本快照、风险预检、人工审核、审计时间线、异步重试和撤回能力。

替换后的唯一入口是：普通用户调用 `POST /api/v1/knowledge-submissions/community`，管理员调用 `POST /api/v1/admin/knowledge-submissions/uploads`。二者都先创建 `PRECHECKING` 投稿，必须经过 RabbitMQ 预检和管理员批准，才允许生成 `READY + APPROVED` 的 RAG 文档。
