## 2. 第四周完整调用链

### 2.1 首次提问

```text
Vue（conversationId 为空）
  → Spring Boot ChatController
  → ChatService 创建 conversation
  → 可选：PetProfileService 读取宠物档案
  → MyBatis 按宠物类型/知识分类读取候选分块
  → FastAPI 进行 Top-K 检索并生成答案
  → Spring Boot 在同一事务写入 USER 与 ASSISTANT 消息
  → Vue 保存响应中的 conversationId
```

因此，从第四周开始，浏览器第一次发送问题时不需要自己生成会话编号。Java 是会话编号的唯一创建方。

### 2.2 后续追问

```text
Vue 携带已有 conversationId
  → Java 验证会话存在
  → MyBatis 读取最近 12 条 USER/ASSISTANT 消息
  → Java 将历史消息、宠物档案和候选知识一起发送给 FastAPI
  → FastAPI 使用最近用户问题增强检索，并把全部有限历史交给模型
  → 本轮问答继续写入同一 conversation
```

如果没有配置 API Key，历史用户问题仍会参与本地向量检索；配置百炼后，历史中的用户与助手消息还会直接参与 `qwen3.7-plus` 的生成过程。

### 2.3 网页知识导入

```text
浏览器读取 .md/.txt 正文
  → POST /api/v1/knowledge/documents
  → FastAPI 清洗、分块、本地向量化
  → Spring Boot 事务写入 knowledge_document 和 knowledge_chunk
  → 网页刷新文档列表并显示 已向量化分块数/总分块数
```

网页不会直接访问 FastAPI，仍然由 Spring Boot 作为唯一业务入口。

## 5. 问答事务设计

`ChatService.answer()` 现在是完整事务边界：

1. `conversationId` 为空时，根据问题前 30 个 Unicode 字符创建标题和会话。
2. `conversationId` 不为空时，先确认会话存在并读取最近消息。
3. 可选读取宠物档案，并以档案的 `petType` 覆盖手工宠物类型筛选。
4. 调用 FastAPI 获得回答。
5. 只有 AI 调用成功后才保存本轮 `USER` 和 `ASSISTANT` 消息。
6. 任一数据库步骤失败时整个事务回滚，避免半轮消息。

直接调用“创建会话”接口时不再立刻写 Redis。会话摘要在第一次读取时才缓存，这样事务回滚不会留下数据库中不存在的幽灵缓存。

## 6. FastAPI 多轮上下文

`RagRequest` 新增：

```json
{
  "history": [
    {"role": "USER", "content": "幼猫一天应该喂几次？"},
    {"role": "ASSISTANT", "content": "……"}
  ],
  "pet_profile": {
    "name": "团子",
    "pet_type": "CAT",
    "age_months": 4,
    "weight_kg": 1.8
  }
}
```

上下文限制：

- Java 最多读取最近 12 条用户/助手消息。
- FastAPI 模型限制最多接收 20 条，实际再次截取最近 12 条。
- 每条历史正文最多 4000 字符。
- 向量检索使用最近两条用户问题加当前问题，改善“那它呢”“这种情况呢”等追问的召回。
- 宠物档案只用于知识过滤和回答措辞，系统提示明确禁止据此做诊断。

第四周响应阶段：

| `stage` | 含义 |
|---|---|
| `week-4-rag-llm` | 命中知识库，百炼根据知识和历史生成 |
| `week-4-rag-local` | 命中知识库，但使用本地抽取式回答 |
| `week-4-general-llm` | 未命中知识库，由通用模型回答并明确标记 |
| `week-4-rag-no-context` | 未命中知识，且通用模型不可用 |

响应还会返回 `modelName`。助手消息写入 MySQL 时也会保存该模型名称，例如 `qwen3.7-plus` 或 `local-extractive`。

## 9. 错误处理

Java 统一返回：

```json
{
  "code": "AI_SERVICE_UNAVAILABLE",
  "message": "AI 服务暂时不可用，请稍后重试",
  "timestamp": "2026-08-16T00:00:00Z"
}
```

新增处理包括：

- `PET_PROFILE_NOT_FOUND`：档案不存在，HTTP 404。
- `INVALID_JSON`：JSON 语法或字段类型不正确，HTTP 400。
- `DATABASE_UNAVAILABLE`：MySQL 操作失败，HTTP 503。
- `INTERNAL_ERROR`：未预期服务器异常，HTTP 500，并在 Java 控制台保留完整日志。
- `AI_SERVICE_UNAVAILABLE`：FastAPI 无法访问，HTTP 502。

浏览器遇到网络错误时会明确提示检查 Spring Boot 8080 端口；遇到 AI 错误时提示检查 FastAPI 8000 端口。

## 13. 当前边界与第五周方向

后续开发采用“完成迁移后删除旧实现”的原则：新功能替代旧功能时，同步删除不再使用的兼容入口、占位响应、旧 DTO、旧分支、无效配置和测试，避免新旧逻辑长期并存。Flyway 已执行的迁移文件除外，它们属于不可修改的数据库版本历史；数据库调整应新增迁移文件。

- 历史消息可以参与检索和生成，但知识向量仍是教学用本地哈希向量。
- 历史消息表目前不保存每次 RAG 来源快照，因此重新打开会话时能看到答案和模型名，但不重新展示旧来源卡片。
- 知识导入进度是同步阶段进度，不是 SSE 实时进度。
- 第四周网页只接受 `.md`、`.markdown` 和 `.txt`，当前不能直接解析 PDF。
- 当前是匿名本地演示，档案和会话尚未绑定登录用户。

### 13.1 第五周 PDF 导入计划

第五周将在现有网页知识导入流程中增加 `.pdf`，并区分两类文档：

1. **文字型 PDF**：后端直接提取页面文本，保留页码信息，经过预览确认后进入清洗、分块和向量化流程。
2. **扫描型 PDF**：检测到页面没有可提取文本时进入 OCR 流程；OCR 作为独立能力封装，避免与普通文本解析代码混在一起。

计划新增的用户流程：

```text
选择 PDF
  → 判断文字型或扫描型
  → 按页提取文本/OCR
  → 网页展示提取预览与页数
  → 用户确认导入
  → 清洗、分块、向量化
  → MySQL 保存文档、分块和页码来源
```

第五周 PDF 功能验收项：

- [ ] 网页文件选择器接受 `.pdf`。
- [ ] 文字型 PDF 能提取正文并显示预览。

### 13.2 第五周混合回答路由优化

第四周混合模式只根据向量相似度阈值判断知识库是否命中。如果低质量分块刚好超过阈值，系统会进入受知识库约束的 RAG 分支；模型虽然已经被调用，但只能回答“现有资料不足”，不会自动切换到通用回答。

第五周将把路由改为两级判断：

```text
第一层：向量检索与重排
  → 没有合格候选：进入通用模型模式
  → 存在候选：进入资料可回答性判断
       → 资料足够：RAG 回答并展示来源
       → 资料不足：通用模型回答，并明确标记“未命中可回答资料”
```

计划验收项：

- [ ] 不再仅凭 `min-score` 决定最终回答模式。
- [ ] 模型或重排器输出结构化的“资料是否足够”结果，避免依赖“无法回答”等字符串匹配。
- [ ] 资料不足时自动切换到 `general-llm`，并且不把低质量分块展示为答案依据。
- [ ] 通用回答必须继续显示“未命中本地知识库”提示。
- [ ] 对“知识库有相似资料但没有答案”的问题增加固定回归测试。
- [ ] 记录每次路由原因、最高相关度和最终阶段，方便排查误路由。
- [ ] 在保证效果的前提下控制模型调用次数，避免不必要地消耗百炼免费额度。

### 13.3 第五周 Redis 缓存重构

第四周保留的 Redis 会话摘要缓存只服务于 `GET /api/v1/conversations/{id}`，当前网页没有调用该接口。按照“不保留未使用旧代码”的开发约定，第五周不继续维护这套低价值摘要缓存，而是把 Redis 用到每次多轮问答都会读取的“最近会话上下文”。

目标读取链路：

```text
ChatService 读取最近 12 条 USER/ASSISTANT 消息
  → 查询 Redis 上下文缓存
       → 命中：直接发送给 FastAPI
       → 未命中：MyBatis 查询 MySQL
                    → 写入 Redis，TTL 30 分钟
                    → 发送给 FastAPI
  → Redis 故障：记录降级日志并继续查询 MySQL
```

推荐缓存键和值：

```text
Key: pet-assistant:conversation:context:{conversationId}:v1

Value:
[
  {"role":"USER","content":"幼猫一天喂几次？"},
  {"role":"ASSISTANT","content":"建议少量多餐……"}
]
```

缓存一致性要求：

1. MySQL 始终是会话和消息的真实数据源，Redis 不能作为唯一存储。
2. 只缓存最近 12 条模型上下文，不缓存无限增长的完整历史消息。
3. 本轮 `USER` 和 `ASSISTANT` 消息成功提交 MySQL 后，再删除对应上下文 Key。
4. 事务回滚时不能提前写入新缓存或产生包含未提交消息的数据。
5. Redis 连接失败、序列化失败或超时时必须自动回退 MySQL，不能让问答接口失败。
6. 缓存结构增加 `v1` 版本后缀，后续字段变化时可以平滑切换新 Key。

第五周 Redis 验收项：

- [x] 删除未被网页使用的会话摘要接口、摘要 DTO、摘要缓存分支和对应旧测试。
- [x] 新增职责单一的 `ConversationContextCacheService`。
- [x] `getRecentMessagesForContext()` 实现 Redis Cache-Aside 模式。
- [x] 首次追问从 MySQL 加载上下文并写入 Redis。
- [x] 再次追问能够命中 Redis，同时保持消息顺序正确。
- [x] 新消息事务提交后使旧上下文缓存失效。
- [x] Redis 未启动时问答和历史消息查询继续正常使用 MySQL。
- [x] 自动化测试覆盖缓存命中、未命中、事务后失效和 Redis 故障降级。
- [x] 日志可以区分 `REDIS` 命中与 `MYSQL` 回源，但不能记录完整用户隐私内容。

知识文档列表和宠物档案列表可以在多轮上下文缓存稳定后再增加短 TTL 缓存。完整历史消息、全部知识向量暂不进入 Redis，避免无界增长和过高内存占用。

## 14. 核心代码讲解（后补）

### 14.1 首次问题如何创建唯一会话

代码位置：`backend/business-service/src/main/java/com/petassistant/business/service/ConversationService.java` 的 `createForQuestion()`。

```java
public ConversationResponse createForQuestion(String question) {
    String normalized = question.trim();
    int[] codePoints = normalized.codePoints().limit(30).toArray();
    String title = new String(codePoints, 0, codePoints.length);
    if (normalized.codePointCount(0, normalized.length()) > codePoints.length) {
        title += "…";
    }
    return create(new CreateConversationRequest(null, title));
}
```

标题只用于展示，真正主键在 `create()` 中使用新的 UUID。即使两个会话的第一个问题完全一样，也只会出现相同标题，不会产生相同 `conversationId`，因此消息不会串线。

使用 Unicode code point 截断而不是 `substring(0, 30)`，是为了避免把 emoji 或扩展字符切成半个字符。调试新会话时观察响应的完整 `conversationId`，不要用标题判断会话是否相同。

### 14.2 问答事务为什么放在 ChatService

代码位置：`backend/business-service/src/main/java/com/petassistant/business/service/ChatService.java` 的 `answer()`。

```java
@Transactional
public ChatResponse answer(ChatRequest request) {
    String conversationId = blankToNull(request.conversationId());
    List<ConversationContextMessage> history;

    if (conversationId == null) {
        ConversationResponse created =
                conversationService.createForQuestion(request.question());
        conversationId = created.id();
        history = List.of();
    } else {
        history = conversationService
                .getRecentMessagesForContext(conversationId, 12);
    }

    AiRagResponse aiResponse = aiServiceClient.answer(aiRequest);
    conversationService.addMessage(
            conversationId,
            new CreateMessageRequest(
                    "USER", request.question().trim(), null, null
            )
    );
    conversationService.addMessage(
            conversationId,
            new CreateMessageRequest(
                    "ASSISTANT", aiResponse.answer(),
                    aiResponse.modelName(), null
            )
    );
    // ……组装 ChatResponse
}
```

核心边界是：只有 AI 成功返回后，USER 与 ASSISTANT 才一起写入。后续任一数据库操作失败会回滚整个事务，避免历史里只剩问题或只剩回答。外部模型调用虽然发生在事务内会延长事务时间，但第四周优先保证教学项目的数据一致性；后续高并发版本可改为任务状态机。

调试时建议在调用 AI 前、保存 USER 后、保存 ASSISTANT 后设置三个断点，并观察事务异常时两条消息是否都没有落库。

### 14.3 宠物档案如何同时影响过滤和 Prompt

```java
PetProfileEntity profile = resolveProfile(request.petProfileId());
String effectivePetType = profile == null

List<RagCandidateRow> rows = knowledgeMapper.findRagCandidates(
```

### 14.4 Vue 如何保存并复用 conversationId

代码位置：`frontend/src/App.vue` 的 `submitQuestion()` 与 `startNewConversation()`。

```ts
const response = await sendQuestion({
  question: content,
  conversationId: conversationId.value,
  petProfileId: selectedProfileId.value || undefined,
})
conversationId.value = response.conversationId

function startNewConversation() {
  conversationId.value = undefined
  messages.value = []
}
```

第一次发送时 ID 为空，由 Java 创建并在响应中返回；下一次发送自动携带该 ID。点击“新建”只清理前端当前状态，不提前创建空会话。这样相同首问仍会生成各自独立的 UUID。

如果 Java 断点看到 `conversationId=null`，应先确认这是第一次发送还是前端在请求后没有执行赋值；浏览器 Network 的响应体必须包含 `conversationId`。

### 14.5 历史会话为何从 MySQL 加载

```ts
const history = await listConversationMessages(id)
conversationId.value = id
messages.value = history
  .filter((message) =>
    message.role === 'USER' || message.role === 'ASSISTANT'
  )
```
